# パターンの語彙と、選ぶ規則

Boxloom が持つ「内容の型」の一覧と、内容からどの型を選ぶかの規則を定める。
方向性(なぜ限られた語彙から選ばせるのか)は `docs/vision.md` の3章。

> 状態: 語彙と規則の第一版。**いま実装があるのは「いまある」の列が ○ のものだけ**。
> ほかは名前と層の案で、入るまでは IR・Markdown では誤りとして断る
> (`docs/content-syntax.md` の「予定」と同じ扱い)。それぞれの実装は Backlog の
> タスク(表の右端)で進める。

## 1. 考え方

- **型は内容の構造で決まる。見た目では決めない。** 「2つの選択肢を同じ観点で比べる」
  「日付のある計画」のように、作者(人・AI)が書く前に判定できる性質で型を選ぶ。
  コンサルティングの資料作り(Zelazny『Say It With Charts』の比較の5分類、Minto の
  ピラミッド原則)が何十年も人手でやってきたことを、閉じた語彙と規則にする。
- **語彙は閉じている。** 知らない型は誤り。型を足すときは、この文書とテンプレートと
  Schema を同時に足す。
- **3つの層に分ける**(`docs/vision.md` の3章):
  1. **スライドの型**と**本文のブロック**(第1層)— テンプレートの部品が、文字と箱で組む。
  2. **キャンバス**(第2層)— サブシステムの枠。テンプレートの骨組みが大きさを決める。
  3. **キャンバスの中の図**(第3層)— サブシステム。自分の座標と寸法の規則を持つ。
     本当に表せないときだけ、生の図形(`shapes`)まで降りる。

## 2. ブロックかサブシステムかの線引き

**要素の位置が意味を持つならサブシステム、位置が読む順序でしかないならブロック。**

| 問い | はい → | いいえ → |
|---|---|---|
| 要素の位置・大きさが値を表すか(時間の軸、数に比例する長さ、2軸の上の位置) | サブシステム | 次へ |
| 要素どうしを線・矢印で繋ぐ、または上下・前後の関係を形で見せるか | サブシステム | 次へ |
| 中に自分の寸法の規則(行の高さ、目盛り、段の幅)が要るか | サブシステム | ブロック |

- **ブロック**は、テンプレートの部品が Box の部分木に組む。大きさは文字の流し込みで
  決まり、はみ出しは `layout-overflow` で測れる。Markdown では本文・囲みで書く。
- **サブシステム**は、自然・最小・上限の大きさを自己申告し(`docs/subsystem.md`)、
  割り当てられた枠の中を自分で組み直す。Markdown では言語名つきのコードブロック
  (中身は YAML)で書く。
- どちらも、色は役割名・字の大きさはテンプレートの段で、作者は見た目を書かない。

### 2.1 表 → ブロック(`table`)

**決定:表は第1層のブロックにする。** PPTX の本物の表(`a:tbl`)で出す。

- 理由:表の中身は文字で、位置は「行と列」という読む順序でしかない(線引きの1・2に
  当たらない)。セルの幅と高さは文字の流し込みで決まり、ブロックと同じ測り方で
  はみ出しを検査できる。Markdown の GFM の表がそのまま入口になる。PowerPoint で
  表として編集できることは、図形の寄せ集めで描くより価値が高い(`docs/vision.md` の4章)。
- 決まり:
  - Markdown は GFM の表。列の配置指定(`:--:` など)は誤り(配置はテンプレート)。
  - セルの中はインライン(強調・コード・リンク・改行)だけ。箇条・囲みは誤り。
  - 1行目は見出しの行。列の幅は中身から測る。行が多すぎて収まらないときは
    `layout-overflow` の警告(自動で次のスライドへ送らない)。
- **マトリクス(`matrix`)との境目**:セルが文字・数なら `table`。セルが**評価**
  (○△×、対応・条件つき・非対応のような状態)で、色や印で見せたいなら `matrix`
  (第3層)。評価を表の文字で「○」と書くのは誤りではないが、規則 R6 で `matrix` を選ぶ。
- 形の細部は Backlog の `pattern-table`(#21)で決める。

### 2.2 画像 → ブロック(`image`・`gallery`)

**決定:画像は第1層のブロックにする。** PPTX の本物の画像(`p:pic`)で出す。

- 理由:画像は中に構造もデータも持たない(線引きの3つともいいえ)。必要なのは
  「縦横比を保って枠に収める」ことだけで、これは文字を持たないので拡大縮小してよい
  (サブシステムで拡大縮小を使わないのは、中の文字がテンプレートの段から外れるため)。
  Markdown の `![代わりの文](path)` がそのまま入口になる。
- 決まり:
  - 代わりの文は必須(読み上げと、画像が無いときのため)。
  - 縦横比を保って枠に収める。切り抜かない。余りをどこに置くかはテンプレート。
  - 1枚は `image`、2〜6枚の並びは `gallery`(1つの段落に画像だけを並べて書く)。
  - ファイルは文書からの相対パス。無い・読めない・形式(PNG・JPEG)が違うものは
    `check` の誤り。SVG を受けるかは未決(`pattern-image` で決める)。
- 形の細部は Backlog の `pattern-image`(#22)で決める。

### 3.4 Zelazny の比較の5分類との対応

Zelazny は数のグラフを、伝えたい「比較」の種類で5つに分けた。Boxloom では次の型で受ける。

| Zelazny の比較 | 例の言い方 | Boxloom の型 |
|---|---|---|
| 構成比(component) | 「売上の 40% が A」 | `chart`(積み上げ・円)、数が1〜2個なら `stat` |
| 項目比較(item) | 「A が B より多い」 | `chart`(横棒)、数が少なければ `stat`・`table` |
| 時系列(time series) | 「年々増えている」 | `chart`(縦棒・折れ線)。日付のある**期間**なら `gantt` |
| 度数分布(frequency) | 「大半が 10〜20 の範囲」 | `chart`(ヒストグラム) |
| 相関(correlation) | 「A が増えると B も増える」 | `chart`(散布図) |

数でない内容(選択肢の比較・手順・構造・因果・主張)は、Minto のピラミッドの
「結論 → 理由の並び」に沿って、`statement`・`takeaway`・`points`・`compare`・
`process`・`orgchart` で受ける。

## 4. 選ぶ規則

**上から順に当てはめ、最初に当たったものを使う。** どれにも当たらなければ R13。
作者が AI のときは、この規則を Skill(`skills/boxloom/SKILL.md`、Backlog #10)で渡す。

前提(どの型でも):スライドの題は「何の話か」ではなく**結論の文**にする
(「移行計画」ではなく「第1世代は 2029 年までに移す」)。1枚で言うことは1つ。

各規則に、良い例(○)と悪い例(×)を1つずつ付ける。悪い例は両方向の失敗
(簡単な内容を図にする/図が要る内容を箇条に押し込む)を含む。

**R1. 章の変わり目 → `section`。**
- ○「第2部 移行の進め方」だけのスライド。
- × 区切りのスライドに箇条で章の目次を書く(目次は `points` の本文スライドにする)。

**R2. 言うことが1文で、根拠はほかのスライドにある → `statement`。** 本文の中で
1文を目立たせたいだけなら `takeaway`。
- ○「移行は 2 年早める必要がある」1文だけ。
- × 結論の1文の下に理由の箇条を5つ足す(それは `content` の題に結論、本文に `points`)。

**R3. 数を1〜4個、強く見せる(比べる相手の系列が無い) → `stat`。**
- ○「対応機種 3 → 12」「問い合わせ −40%」の2つ。
- × 5年分の推移を `stat` を5つ並べて見せる(系列なので R4 の `chart`)。

**R4. 数の系列(3点以上)で、比較・推移・構成比・分布・相関を見せる → `chart`**
(3.4 の対応で種類を選ぶ)。`chart` が入るまでは `table` で書く。
- ○ 四半期ごとの利用者数8点を折れ線で。
- × 2つの数(去年と今年)を棒グラフにする(R3 の `stat` で足りる)。

**R5. 日付のある期間・計画 → `gantt`。** 日付が無く順序だけなら R7。
- ○ 機種ごとの保守の期限と移行の期間。
- × 「計画」を年ごとの箇条で書き、期間の重なりを読者に頭の中で組み立てさせる。

**R6. 行×列で、セルが評価(状態) → `matrix`。** セルが文字・数 → `table`。
- ○ 3つの案 × 5つの要件を、対応・条件つき・非対応で。
- × 2つの案を2つの観点で比べるだけのものを `matrix` にする(R8 の `compare` で足りる)。

**R7. 日付の無い、方向のある段階(3〜7段階) → `process`。** 2段階なら `points`
か `compare`、8段階以上なら分けるか段階をまとめる。
- ○「申請 → 審査 → 承認 → 反映」。
- × 手順4つを番号つきの箇条で書き、前の段の出力が次の段の入力になる関係を見えなくする。

**R8. 2つ以上の選択肢を、それぞれの良い点・悪い点で比べる → `compare`。**
観点がどの選択肢にも共通で3つ以上あるなら R6 の `matrix` か `table`。
- ○ 案 A・案 B のそれぞれに良い点2つ・悪い点1つ。
- × 1つの案の良い点・悪い点だけを `compare` に入れる(比べる相手が無い。良い点と
  悪い点を `points` で書く)。

**R9. 上下の関係(親1つ・子 2〜8) → `orgchart`。**
- ○ 推進体制:責任者1人と、その下の4チーム。
- × 階層の無い4つのチームを `orgchart` で横に並べる(関係が無いので `columns` か `points`)。

**R10. 段階ごとに数が減る → `funnel`。**
- ○ 訪問 10,000 → 登録 1,200 → 有料 90。
- × 減っていかない段階(手順)を `funnel` で描く(R7 の `process`)。

**R11. 他人の言葉 → `quote`。**
- ○ 利用者インタビューの一言と、出どころ(「利用者 A、2026 年 9 月」)。
- × 自分の結論を引用の形にして権威づける(`takeaway`)。

**R12. 2〜3個の並列のまとまりを並べて読ませる → `columns`。** 並列が4つ以上・
それぞれ1行なら `points`。
- ○「今年やること/来年やること/やらないこと」に、それぞれ箇条2〜3。
- × 1つの論の続き(前の段を読まないと次が分からない)を段に分ける(`paragraph` か `points`)。

**R13. どれにも当たらない文章 → `points`(並列の論点)か `paragraph`(つながった文章)。**
- ○ 背景の説明を2〜3文の段落で。
- × 要素どうしの関係が肝なのに箇条に流す(R7・R9 を見直す。関係が上のどの形でもなければ R14)。

**R14. 最後の手段:要素の位置・繋がりが意味を持つのに、R1〜R12 のどの型の形でもない
→ `shapes`。** 使ってよいのは次を全部満たすときだけ:
1. R1〜R12 を順に当て、当たらない理由を言える(Skill では理由を発表者ノートではなく
   作者への返事に書かせる)。
2. 図形が 3 個以上あり、繋がり・位置に意味がある(2個以下なら `points` か `compare`)。
3. 既存の型と同じ形を描かない。箱を矢印で横に並べる → `process`、親と子の箱 → `orgchart`、
   格子に評価を置く → `matrix`。
- ○ 架空のシステム構成図(利用者・Web 層・API 層・保存先と、その間の流れ)。
  `examples/md/shapes.bx.md`。
- × 「申請 → 審査 → 承認」を `shapes` の箱と矢印で描く(R7 の `process`)。

`shapes` が繰り返し同じ形で使われたら、それは**語彙が足りないしるし**である。
新しい型の候補としてこの文書と Backlog に足す(テンプレートの審美の持ち主が決める。
`docs/vision.md` の6章)。

## 6. この文書を変えるとき

- 型を足す・変えるときは、3章の表、4章の規則、`docs/content-syntax.md`(記法)、
  `docs/ir.md` と `schema/`(IR)、テンプレートの部品、`boxloom schema` の出力を
  同時に揃える。
- 規則を変えるときは、良い例と悪い例を必ず付ける。
