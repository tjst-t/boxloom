# パターンの語彙と、選ぶ規則

Boxloom が持つ「内容の型」の一覧と、内容からどの型を選ぶかの規則を定める。
方向性(なぜ限られた語彙から選ばせるのか)は `docs/vision.md` の3章。

> 状態: 語彙と規則の第一版。**いま実装があるのは「いまある」の列が ○ のものだけ**
> (文字のパターン section・statement・takeaway・stat・quote は 3.2.1)。
> ほかは名前と層の案で、入るまでは IR・Markdown では誤りとして断る
> (`docs/content-syntax.md` の「予定」と同じ扱い)。それぞれの実装は Backlog の
> タスク(表の右端)で進める。

## 1. 考え方

- **型は内容の構造で決まる。見た目では決めない。** 「2つの選択肢を同じ観点で比べる」
  「日付のある計画」のように、作者(人・AI)が書く前に判定できる性質で型を選ぶ。
  コンサルティングの資料作り(Zelazny『Say It With Charts』の比較の5分類、Minto の
  ピラミッド原則)が何十年も人手でやってきたことを、閉じた語彙と規則にする。
- **語彙は閉じている。** 知らない型は誤り。型を足すときは、この文書とテンプレートと
  Schema を同時に足す。
- **3つの層に分ける**(`docs/vision.md` の3章):
  1. **スライドの型**と**本文のブロック**(第1層)— テンプレートの部品が、文字と箱で組む。
  2. **キャンバス**(第2層)— サブシステムの枠。テンプレートの骨組みが大きさを決める。
  3. **キャンバスの中の図**(第3層)— サブシステム。自分の座標と寸法の規則を持つ。
     本当に表せないときだけ、生の図形(`shapes`)まで降りる。

## 2. ブロックかサブシステムかの線引き

**要素の位置が意味を持つならサブシステム、位置が読む順序でしかないならブロック。**

| 問い | はい → | いいえ → |
|---|---|---|
| 要素の位置・大きさが値を表すか(時間の軸、数に比例する長さ、2軸の上の位置) | サブシステム | 次へ |
| 要素どうしを線・矢印で繋ぐ、または上下・前後の関係を形で見せるか | サブシステム | 次へ |
| 中に自分の寸法の規則(行の高さ、目盛り、段の幅)が要るか | サブシステム | ブロック |

- **ブロック**は、テンプレートの部品が Box の部分木に組む。大きさは文字の流し込みで
  決まり、はみ出しは `layout-overflow` で測れる。Markdown では本文・囲みで書く。
- **サブシステム**は、自然・最小・上限の大きさを自己申告し(`docs/subsystem.md`)、
  割り当てられた枠の中を自分で組み直す。Markdown では言語名つきのコードブロック
  (中身は YAML)で書く。
- どちらも、色は役割名・字の大きさはテンプレートの段で、作者は見た目を書かない。

### 2.1 表 → ブロック(`table`)

**決定:表は第1層のブロックにする。** PPTX の本物の表(`a:tbl`)で出す。

- 理由:表の中身は文字で、位置は「行と列」という読む順序でしかない(線引きの1・2に
  当たらない)。セルの幅と高さは文字の流し込みで決まり、ブロックと同じ測り方で
  はみ出しを検査できる。Markdown の GFM の表がそのまま入口になる。PowerPoint で
  表として編集できることは、図形の寄せ集めで描くより価値が高い(`docs/vision.md` の4章)。
- 決まり:
  - Markdown は GFM の表。列の配置指定(`:--:` など)は誤り(配置はテンプレート)。
  - セルの中はインライン(強調・コード・リンク・改行)だけ。箇条・囲みは誤り。
  - 1行目は見出しの行。列の幅は中身から測る。行が多すぎて収まらないときは
    `layout-overflow` の警告(自動で次のスライドへ送らない)。警告の hint と容量に
    分け方の案(何枚に・どの行の前で)が付く。
  - 長い表は作者がスライドごとに分け、続きの表に `continues`(Markdown は `{continues}`)を
    書く。続きの表は見出しの行を書かず、Boxloom が各枚に最初の表の見出しの行と「n/m」の
    印を付け、列の幅を全部の枚でそろえる(`docs/ir.md` の設計判断14)。
- **マトリクス(`matrix`)との境目**:セルが文字・数なら `table`。セルが**評価**
  (○△×、対応・条件つき・非対応のような状態)で、色や印で見せたいなら `matrix`
  (第3層)。評価を表の文字で「○」と書くのは誤りではないが、規則 R6 で `matrix` を選ぶ。
  `matrix` のセルは評価(`status`)が必須で、色の丸と凡例で見せる。評価の無いセルを
  書きたくなったら、その表は `table`。書き方は `docs/subsystem.md` の11節。
- 形(#21 で決めた):IR は `{type: "table", header: [セル…], rows: [[セル…]…], caption?}`。
  セルはインライン。列の幅と行の高さはテンプレートが中身から測り(`docs/fonts.md` の
  字体の幅)、割り当てられた幅いっぱいに広げる。数だけの列は右に揃える(dark / light の
  方針。数かどうかはテンプレートが中身から見る)。見出しの行の塗りは `card_alt`、本体は
  `card`、行の間の線は `grid`(役割名)。書き方は `docs/content-syntax.md` の 3.7。

### 2.2 画像 → ブロック(`image`・`gallery`)

**決定:画像は第1層のブロックにする。** PPTX の本物の画像(`p:pic`)で出す。

- 理由:画像は中に構造もデータも持たない(線引きの3つともいいえ)。必要なのは
  「縦横比を保って枠に収める」ことだけで、これは文字を持たないので拡大縮小してよい
  (サブシステムで拡大縮小を使わないのは、中の文字がテンプレートの段から外れるため)。
  Markdown の `![代わりの文](path)` がそのまま入口になる。
- 決まり:
  - 代わりの文は必須(読み上げと、画像が無いときのため)。
  - 縦横比を保って枠に収める。切り抜かない。余りをどこに置くかはテンプレート。
  - 1枚は `image`、2〜6枚の並びは `gallery`(1つの段落に画像だけを並べて書く)。
  - ファイルは文書からの相対パス。無い・読めない・形式(PNG・JPEG)が違うものは
    `check` の誤り(`image-missing`・`image-format`)。**SVG は受けない**(#22 で決めた。
    PPTX の SVG は PNG の代わりの絵も要り、依存ゼロで作れないため。PNG にして渡す)。
- 形(#22 で決めた):IR は `{type: "image", src, alt, caption?}` と
  `{type: "gallery", images: [{src, alt, caption?}…]}`(2〜6枚)。ライブラリはファイルを
  読まないので、画像は呼ぶ側が渡す `fs.FS`(`BuildOptions.Assets`・`CheckOptions.Assets`。
  根は文書のフォルダ)から読む(`docs/library.md`)。**画像と文を横に並べる**のは画像の
  属性ではなく `columns`(まとまりの1つに画像、もう1つに文)で書く。書き方は
  `docs/content-syntax.md` の 3.8。

### 2.3 並列のまとまり → ブロック(`columns`)

**決定(#20):** 並列のまとまりは第1層のブロック。段組み(「2段に分ける」という
見た目の指定)ではなく、「この2〜3個は並べて読むもの」という意味を持つ。

- IR は `{type: "columns", columns: [{title?, role?, body: [ブロック…]}…]}`(2〜3個)。
  まとまりの題 `title` は意味の一部(小見出しを持たない代わりに、ここで持つ)。
- **幅の比は意味で書く。** 数(`width: 2`・`60%`)は書けない。まとまりの1つを
  `role: "main"`(主のまとまり。ほかはそれを補う)にすると、テンプレートがそれを広く取る
  (dark / light は `columnMainWeight` = 2 倍)。付けなければ同じ幅(並列で対等)。
  `role` の値はいまは `main` だけ(補う側に名前を付ける `aside` などは、要る例が出たら足す)。
- 中に置けるのは段落・箇条・注記・表・画像・画像の並び・対の並び(pairs)・数値のグラフ
  (chart)・循環の図(cycle)・フェーズの図(phases)・評価の格子(matrix)・組織図(orgchart)・
  屋根と柱の図(pillars)(#117・#121)。`columns` の入れ子・比較・ほかのサブシステム(gantt・process・funnel・shapes)は
  置けない(本文の幅を前提にする図と、入れ子で並列の意味がぼやけるもの)。
- **使う時(#117)**:図や対の並びの横に、それを読むための文を置きたいとき。図のまとまりと
  文のまとまりを並べ、主なほうに `role: main` を付ける。
  - 対の並び(pairs)の横に、そこから抜き出した論点の一覧(左に一覧・右に対)。
  - フェーズの図(phases)の横に、段ごとの要点(段の箱に長い説明を詰めない)。
  - 評価の格子(matrix)の横に、読み取り(どの案が何を満たすか)。
  - 組織図(orgchart)の横に、体制の要点(足りない担当・役割の分け方)。
  - 画像の並び(gallery)の横に、手順・見どころ(左に番号つきの箇条・右に写真)。
  図はまとまりの幅で測る。文が箱に入らない幅しか無ければ、まとまりは図の要る幅まで広がり、
  それでも足りなければ図の警告になる(図を縮めて詰めない)。図を全幅で見せたいなら
  まとまりに入れず、文は lead や次のスライドに書く。グラフは「左にグラフ・右に読み取り」の
  形で置ける(軸・ラベルの置き場所はアプリが決めるので、狭い枠でも読める)。循環の図(#91)は
  「左に輪・右に段ごとの説明」の形で置ける(輪は縦横比を保つので、全幅に1つだけ置くと横が
  空く。段ごとの長い説明を輪の中に詰めず、横のまとまりに書く)。屋根と柱の図(#121)も「左に図・右に
  柱ごとの説明」の形で置ける。
- はみ出しはまとまりごとに測り、一番高いまとまりがブロックの高さを決める
  (`docs/ir.md` の「はみ出し」)。
- **流れ(#84):** 左のまとまりが右のまとまりにつながる(背景→ゴール、発見→対応、
  前提→結論)ときは `flow: true`(Markdown は `:::::columns {flow=true}`)。意味だけを書き、
  印(矢印・丸)はテンプレートが描く。

### 2.4 対の並び → ブロック(`pairs`。標準でない型)

**決定(#65、`docs/layers.md` の8.1):** 「分かったこと ↔ 打ち手」のように、2つの側の
見出しを1回だけ書き、その下に行ごとに対応する対を並べるものは、第1層のブロック `pairs`。
外の資料では最も多い型だったが、発表用のスライドでは少ないので標準の型にはせず、型の語彙に
足した最初の標準でない型にした。

- 位置そのものに意味は無く「対の2つの側の行がそろう」ことだけが要るので、サブシステムでは
  なくブロック(部品)にする(2章の線引き)。`columns` では2つのまとまりの行がそろわない。
- 側の名前は意味で付ける:`subject`(その対が何についてか)・`response`(それに応えるもの)。
  左右は書かない。側の中身は段落・箇条・引用のどれか1つか、見出し(要因の名前など)と
  段落・箇条・引用・画像・表の1〜4個(#87。読む資料の詳細のページの「見出し+箇条」
  「箇条+引用」の側)。
- 組み方を持たないテンプレートは `columns`(見出しがまとまりの題)で組み、警告
  `component-fallback` を出す。読めるが、行はそろわない。
- はみ出しは対ごとに測る(`docs/ir.md` の「はみ出し」)。

### 2.5 印つきの塊の並び → ブロック(`topics`。標準でない型)

**決定(#119):** いくつかの観点を、それぞれ題と説明で上から順に並べるもの(読む資料の
「A・B・C の丸い印を左に持つ、題と箇条の塊を縦に並べ、塊の間を罫線で区切る」ページ)は、
第1層のブロック `topics`。`pairs` と同じく型の語彙に足した標準でない型。

- 位置に意味は無く「塊ごとに題と中身がまとまり、上から読む」ことだけが要るので、
  ブロック(部品)にする。`points` の太字の段落で「A」を字で書くと、印と罫線を
  テンプレートが描けない。左右の対応が無いので `pairs` ではなく、横に並べないので
  `columns` でもない。
- 塊は題・短い印(任意、全てに付けるか全てに付けない)・中身(段落・箇条・引用の1〜3個)。
- 組み方を持たないテンプレートは箇条(題を親、中身を子)で組み、警告 `component-fallback`。
- はみ出しは塊ごとに測る(`docs/ir.md` の「はみ出し」)。
### 2.6 人物の紹介 → ブロック(`people`。標準でない型)

**決定(#120):** 人の写真・名前・役職・経歴を並べるものは、第1層のブロック `people`。
写真と文の位置の関係(写真の右に名前と経歴)だけが要るのでサブシステムではなく部品にする。
画像と箇条を別々に置くと、画像の最小の高さで本文がはみ出す。写真の大きさ・形・横に並べるか
縦に積むかはテンプレートが決める。組み方を持たないテンプレートは `columns` で組む。

## 3. 語彙の一覧

「いまある」:○ 実装あり/— まだ無い。優先は ★★★(先に)〜★(あとで)。

|---|---|---|---|---|---|
| 表紙 | `cover` | 文書の題・副題・作者 | ○ | — | — |
| 本文 | `content` | 題(短い見出し)・リード文(結論の文)とブロックの並び | ○ | — | — |
| 区切り | `section` | 章の変わり目(章の題だけ) | ○ | — | #17 |
| 主張 | `statement` | このスライドで言うことが1文だけ | ○ | — | #17 |

### 3.2.2 根拠の置き場所(#47)

本文のブロックではない(読む流れに入らない)が、資料の根拠を示す意味。置き場所と見た目は
テンプレートの骨組みが決める。記法は `docs/content-syntax.md` の3.1・3.6.1・3.7、IR は
`docs/ir.md` の設計判断11。例は `examples/md/evidence.bx.md`。

| 意味 | IR | Markdown | dark / light の置き場所 |
|---|---|---|---|
| スライドの出典(出どころ・母数・時点) | スライドの `source` | スライドの一番外側の `:::source` | 本文の下・フッターの上(「出典:」) |
| 文書の日付 | `meta.date` | 文書の頭の `date` | 表紙 |
| 機密区分 | `meta.confidential` | 文書の頭の `confidential` | 表紙とフッター |
| 文書全体の免責・但し書き | `meta.disclaimer` | 文書の頭の `disclaimer` | 表紙(1回) |
| 表の合計の行 | `table` の `total` | 表の説明の行の `{total=last}` | 表の最後の行(太字・上に濃い線) |
| 表の行の群(「プロセス」「体制」などのまとまり) | `table` の `groups` | 表の説明の行の `{groups=first}`、続きの行の先頭のセルは空 | 先頭の列の縦に結合したセル(太字) |
| 2列目以降で同じ値が続くセル(「支援事業」など) | `table` の `groupColumns` | `{groups=列名}`(`,` で複数)、続きの行のその列のセルは空 | その列の縦に結合したセル(左の群の境で切れる) |
| 表の続き(長い表の2枚目から) | `table` の `continues` | 見出しの行を書かずに区切りの行から始め、説明の行に `{continues}` | 最初の表の見出しの行を繰り返し、説明の行の右端に「n/m」 |

- **決まり:数・表・図・引用を見せるスライドには出典を付ける**(型を選ぶ R1〜R14 とは別に、どの型にも掛かる)。出どころ・母数・時点は
  `:::source`。但し書き(数の読み方の注意)は `note`、他人の言葉の出どころは `quote`。
  - ○ stat の下に「問い合わせの記録 12,480 件(2026 年 4〜9 月)の集計」。
  - × 「数字は架空です」「(デモ)」をスライドごとの `note` に繰り返す(文書の頭の
    `disclaimer` に1回)。
  - × 結論や大事な数を `note`・`source` の小さな字に書く(それは題・本文・`takeaway`)。

### 3.2.1 文字のパターンの形(#17・#18・#19 で決めたこと)

例は `examples/md/text-patterns.bx.md`(↔ `examples/ir/text-patterns.json`)。
記法の詳細は `docs/content-syntax.md` の3.2・3.4、IR は `docs/ir.md` の設計判断9。

| 型 | IR | Markdown |
|---|---|---|
| `section` | `{type: "section", title, notes?}` | `# 第2部 移行の進め方 {type=section}` |
| `statement` | `{type: "statement", content, notes?}` | `# 移行は 2 年早める必要がある {type=statement}` |
| `takeaway` | `{type: "takeaway", content}` | `:::takeaway` の中に段落1つ |
| `stat` | `{type: "stat", items: [{value, unit?, label}]}`(1〜4個) | `::::stat` の中に `:::value 3 → 12 {unit=機種}`(中の段落が説明) |
| `quote` | `{type: "quote", content, source}` | `:::quote 利用者 A、2026 年 9 月` の中に段落1つ |

- **区切りと主張は本文を持たない。** IR に `body` が無い(書けば Schema で断る)。Markdown では
  `# …` の行の文がそれぞれ章の題・言いたい1文になり、`:::notes` 以外の本文は誤り
  (R1・R2 の「×」の例、目次の箇条や理由の箇条を足す失敗を記法で止める)。
- **主張の1文は `title` ではなく `content`。** 本文のスライドの題は「本文の上に立つ結論」
  だが、主張のスライドは1文そのものが中身なので、段落・結論と同じ `content` にした。
  PPTX では区切りの題も主張の1文も題のプレースホルダー(レイアウト Title Only)に書くので、
  アウトライン表示では見出しとして読める。
- **章の一覧と現在地はテンプレートが描く。** 文書に区切りが2つ以上あれば、区切りのスライドの
  題の下に、全部の区切りの題を順に並べ、いまの章だけを目立たせる(左の帯がアクセントの色、
  題が太字)。IR の区切りの並びから作るので、作者は何も書かない(目次を手で書く R1 の「×」は
  要らなくなる)。出す・出さないは値の表の `sectionTracker`(docs/template-values.md)。
- **数は書いたとおりの文字列。** `"3 → 12"`・`"−40"` を数に直すと書き方(矢印・
  全角の負の記号・桁区切り)が失われ、計算もしないので文字のまま持つ。数字を1つも含まない
  ものは誤り(数でない言葉を目立たせたいなら `takeaway`)。単位は分けて持ち、どう添えるか
  (大きさ・間)はテンプレートが決める。5つ以上は誤り(R3・R4:系列は `table`・`chart`)。
- **引用の出どころは必須。** R11 の「他人の言葉」は出どころと対で意味を持つ。出どころの無い
  引用は自分の結論を権威づける形(R11 の「×」)になるので、IR でも Markdown でも断る。
  空白だけの出どころ・章の題などは `boxloom check` の `empty-text` で断る。

### 3.4 Zelazny の比較の5分類との対応

Zelazny は数のグラフを、伝えたい「比較」の種類で5つに分けた。Boxloom では次の型で受ける。
`chart` では作者はこの比較の種類を `compare` に書き、グラフの形はサブシステムが選ぶ
(形は見た目なので書けない。`docs/subsystem.md` の12節)。

| Zelazny の比較 | 例の言い方 | Boxloom の型(`chart` の `compare` → 形) |
|---|---|---|
| 構成比(component) | 「売上の 40% が A」 | `chart`(`component` → 円。部分は6つまで、小さい部分は「その他」にまとめる。内訳の推移は `timeSeries` の `stacked`)。数が1〜2個なら `stat` |
| 項目比較(item) | 「A が B より多い」 | `chart`(`item` → 横棒)、数が少なければ `stat`・`table` |
| 時系列(time series) | 「年々増えている」 | `chart`(`timeSeries` → 点が少なく1系列なら縦棒、それ以外は折れ線)。日付のある**期間**なら `gantt` |
| 度数分布(frequency) | 「大半が 10〜20 の範囲」 | `chart`(`frequency` → ヒストグラム) |
| 相関(correlation) | 「A が増えると B も増える」 | `chart`(`correlation` → 散布図) |

数でない内容(選択肢の比較・手順・構造・因果・主張)は、Minto のピラミッドの
「結論 → 理由の並び」に沿って、`statement`・`takeaway`・`points`・`compare`・
`process`・`orgchart` で受ける。

## 4. 選ぶ規則

**上から順に当てはめ、最初に当たったものを使う。** どれにも当たらなければ R13。
作者が AI のときは、この規則を Skill(`skills/boxloom/SKILL.md`、Backlog #10)で渡す。

前提(どの型でも):本文のスライドの題は何の話かを短く名指す**見出し**(1行)にし、
言うことは**リード文**(`:::lead`)に**結論の文**で書く(題「移行の時期」、リード文
「第1世代は 2029 年までに移す」)。1枚で言うことは1つ。区切りの題と主張の1文は、
それ自体が言うことなので、リード文を持たない。

各規則に、良い例(○)と悪い例(×)を1つずつ付ける。悪い例は両方向の失敗
(簡単な内容を図にする/図が要る内容を箇条に押し込む)を含む。

**R1. 章の変わり目 → `section`。**
- ○「第2部 移行の進め方」だけのスライド。
- × 区切りのスライドに箇条で章の目次を書く(目次は `points` の本文スライドにする)。

**R2. 言うことが1文で、根拠はほかのスライドにある → `statement`。** 本文の中で
1文を目立たせたいだけなら `takeaway`。
- ○「移行は 2 年早める必要がある」1文だけ。
- × 結論の1文の下に理由の箇条を5つ足す(それは `content` の題に結論、本文に `points`)。

**R3. 数を1〜4個、強く見せる(比べる相手の系列が無い) → `stat`。**
- ○「対応機種 3 → 12」「問い合わせ −40%」の2つ。
- × 5年分の推移を `stat` を5つ並べて見せる(系列なので R4 の `chart`)。

**R4. 数の系列(3点以上)で、比較・推移・構成比・分布・相関を見せる → `chart`**
(3.4 の対応で `compare` を選ぶ)。系列は3つまで、強調は1つに絞る(Zelazny の「言いたい
1点を目立たせる」)。
- ○ 四半期ごとの利用者数8点を `timeSeries` で(縦棒か折れ線かはサブシステムが選ぶ)。
- × 2つの数(去年と今年)を棒グラフにする(R3 の `stat` で足りる)。

**R5. 日付のある期間・計画 → `gantt`。** 日付が無く順序だけなら R7。
- ○ 機種ごとの保守の期限と移行の期間。
- × 「計画」を年ごとの箇条で書き、期間の重なりを読者に頭の中で組み立てさせる。

**R6. 行×列で、セルが評価(状態) → `matrix`。** セルが文字・数 → `table`。
- ○ 3つの案 × 5つの要件を、対応・条件つき・非対応で。
- × 2つの案を2つの観点で比べるだけのものを `matrix` にする(R8 の `compare` で足りる)。

**R7. 日付の無い、方向のある段階(3〜7段階) → `process`。** 2段階なら `points`
か `compare`、8段階以上なら分けるか段階をまとめる。
- ○「申請 → 審査 → 承認 → 反映」。
- × 手順4つを番号つきの箇条で書き、前の段の出力が次の段の入力になる関係を見えなくする。

**R7a. 段(フェーズ。2〜5段)ごとに、その段でやること(題と箇条)が2つ以上ある
→ `phases`。** R7 の `process` より先に当てる。段に題と短い説明しか無いなら `process`、
日付のある期間なら R5 の `gantt`。いくつかの段をまとめる名前(「調べ」が Step1・2、
「報告書」が Step3)は `groups` の帯に書き、段の題には書かない。箱の番号は段をまたいで
通しでテンプレートが振る(書かない)。
- ○ Step1〜3(題と期間)の下に、それぞれ2〜3個の箱(調べること・作るもの)と箇条。
- × 段ごとの作業を `process` の detail に詰め込み、段の下に長い補足を並べる。
- × 段に箱が1つずつしか無いものを `phases` にする(R7 の `process` で足りる)。

**R7b. 最後の段が最初の段に戻る(繰り返す)段階(3〜6段) → `cycle`。** 戻らない
段階は R7 の `process`。段ごとに長い説明があるなら、`columns` の1つのまとまりに輪、
もう1つに段ごとの箇条を置く(R12)。
- ○「場を知る → 仲間を集める → 小さく試す → 形にする → ふり返る」を毎年回す。
- × 一度きりの手順を輪にして、終わりが始まりにつながるように見せる(R7 の `process`)。

**R7c. 1つの目指す姿を、いくつかの並ぶ要因が支え、共通の前提の上に立つ(要因 2〜6) →
`pillars`。** 上(目指す姿)・並ぶ(要因)・下(前提)の位置が意味を持つのでサブシステム。
要因に順序があるなら R7 の `process`、要因が目指す姿を支える関係でなく並べて読むだけなら
`columns` か `points`。柱ごとの長い説明は、`columns` の1つのまとまりに図、もう1つに柱ごとの
箇条を置く(R12)。
- ○「居場所になる」(屋根)を「場をひらく・担い手を育てる・声を集める」(柱)が支え、
  「住民の参加」(土台)の上に立つ。
- × 順に進む手順を柱にする(R7 の `process`)。× 柱1本に長い段落を詰める。

**R8. 2つ以上の選択肢を、それぞれの良い点・悪い点で比べる → `compare`。**
観点がどの選択肢にも共通で3つ以上あるなら R6 の `matrix` か `table`。
- ○ 案 A・案 B のそれぞれに良い点2つ・悪い点1つ。
- × 1つの案の良い点・悪い点だけを `compare` に入れる(比べる相手が無い。良い点と
  悪い点を `points` で書く)。

**R9. 上下の関係(親1つ・子 2〜8) → `orgchart`。**
- ○ 推進体制:責任者1人と、その下の4チーム。
- × 階層の無い4つのチームを `orgchart` で横に並べる(関係が無いので `columns` か `points`)。

**R10. 段階ごとに数が減る → `funnel`。**
- ○ 訪問 10,000 → 登録 1,200 → 有料 90。
- × 減っていかない段階(手順)を `funnel` で描く(R7 の `process`)。

**R11. 他人の言葉 → `quote`。**
- ○ 利用者インタビューの一言と、出どころ(「利用者 A、2026 年 9 月」)。
- × 自分の結論を引用の形にして権威づける(`takeaway`)。

**R12a. 2つの側(分かったこと/打ち手、課題/対策、問い/答え)の見出しが共通で、
その下に1対1で対応する組が2つ以上ある → `pairs`。** R12 の `columns` より先に当てる。
組が1つなら段落か `columns`、側が3つ以上・セルが評価なら R6 の `matrix` か `table`。
- ○「分かったこと | 打ち手」の下に、聞き取りで分かったことと、それぞれへの打ち手を4組。
- × 対応する組を `columns` の2つのまとまりに分けて書き、どの打ち手がどの発見に応えるかを
  読者に行の高さで数えさせる。
- × 対応の無い2つのリスト(今年やること/来年やること)を `pairs` にする(R12 の `columns`)。

**R12b. いくつかの観点を、それぞれ題と説明で(2〜6個、上から順に)→ `topics`。**
観点ごとに説明が段落・箇条の1〜3個ある。観点に A・B・C のような印で後から触れるなら
`label` を全てに付ける。説明が1行ずつなら `points`、2つの側が対応するなら R12a の `pairs`、
2〜3個を横に並べて見比べるなら R12 の `columns`。
- ○「通いやすさ/続けやすさ/公平さ」の3つの観点に、それぞれ箇条2つや段落と引用。
- × 太字の段落で「A 通いやすさ」と書き、その下に箇条を置く(印と罫線をテンプレートが描けない)。
- × 1行で済む観点を塊にする(`points`)。

**R12c. 人(体制・登壇者・助言者)の写真・名前・役職・経歴を並べる → `people`。**
- ○ 調査の体制の3人を、写真と役職と経歴の箇条で。
- × 画像と箇条を `columns` に別々に置く(写真が大きくなり、行がそろわない)。

**R12. 2〜3個の並列のまとまりを並べて読ませる → `columns`。** 並列が4つ以上・
それぞれ1行なら `points`。
- ○「今年やること/来年やること/やらないこと」に、それぞれ箇条2〜3。
- × 1つの論の続き(前の段を読まないと次が分からない)を段に分ける(`paragraph` か `points`)。
- ○ 左のまとまりが右につながる(背景→ゴール、発見→対応)なら `flow: true` を付ける
  (それぞれが1行の手順なら R7 の `process`)。
- × 対等な並列(今年/来年)に `flow` を付ける(つながりの無いものに矢印が出る)。

**R13. どれにも当たらない文章 → `points`(並列の論点)か `paragraph`(つながった文章)。**
- ○ 背景の説明を2〜3文の段落で。
- × 要素どうしの関係が肝なのに箇条に流す(R7・R9 を見直す。関係が上のどの形でもなければ R14)。

**R14. 最後の手段:要素の位置・繋がりが意味を持つのに、R1〜R12 のどの型の形でもない
→ `shapes`。** 使ってよいのは次を全部満たすときだけ:
1. R1〜R12 を順に当て、当たらない理由を言える(Skill では理由を発表者ノートではなく
   作者への返事に書かせる)。
2. 図形が 3 個以上あり、繋がり・位置に意味がある(2個以下なら `points` か `compare`)。
3. 既存の型と同じ形を描かない。箱を矢印で横に並べる → `process`、親と子の箱 → `orgchart`、
   格子に評価を置く → `matrix`。
- ○ 架空のシステム構成図(利用者・Web 層・API 層・保存先と、その間の流れ)。
  `examples/md/shapes.bx.md`。
- × 「申請 → 審査 → 承認」を `shapes` の箱と矢印で描く(R7 の `process`)。

`shapes` が繰り返し同じ形で使われたら、それは**語彙が足りないしるし**である。
新しい型の候補としてこの文書と Backlog に足す(テンプレートの審美の持ち主が決める。
`docs/vision.md` の6章)。
