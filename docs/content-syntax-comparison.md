# コンテンツの記法の比較

Boxloom の作者が書く「コンテンツ(意味の木)」を、どの記法で書かせるかを比べる
ための文書。**同じ3枚のスライド** を各記法で書き、人が書く・読むときの感触と、
AI が書く・直すときの扱いやすさを並べる。

> 状態: 検討用の資料(決定は末尾と `docs/content-syntax.md`)。サンプルは「こう書けたら」
> という案で、要素の名前・属性の名前は仮。

## 前提: 記法の下に「意味の中間表現」を置く

どの記法を選んでも、パーサーが同じ **意味の中間表現(IR)** に変換し、
テンプレートはその IR だけを見る、という形にする前提で比べている。

```
記法A ─┐
記法B ─┼─→ 意味の IR(JSON Schema で定義)─→ テンプレート ─→ Box の木 ─→ PPTX
記法C ─┘
```

こうしておくと、記法は「入口」にすぎなくなる。複数の記法を並べて持つこともでき、
AI に IR(JSON)を直接書かせる道も残る。**本当に固めるべき約束事は記法ではなく
IR** である。記法選びは「主な入口をどれにするか」の問題になる。

## 共通のお題(3枚)

どの記法のサンプルも、次の内容を書いている。中身は `boxloom/gantt.go` のデモ
データを縮めたもの。

1. **表紙**: 題「ランタイム移行計画」、副題「ハードウェア世代ごとの選択肢と
   期限」、作者「Boxloom デモ」。
2. **論点**: 箇条3つ(1つに強調あり)+「Loom 継続」と「Weft OS 移行」の
   比較(それぞれ良い点・悪い点)+注記「期日はすべてイメージ」。
3. **Gantt**: 期間 2026-09〜2034-11、目盛り1つ(2029-12「Board A・Store X」状態
   danger)、節目1つ(2028-05「ライセンス更新」)、凡例3つ、グループ1つ
   (第1世代 / Board A / 120台 / Store X、ハードウェアのリスク帯 2029-12〜2031-02)、
   行2つ(Loom 2・Loom 3、どちらも「固定版」)、注釈1つ(2029-12 に強調・下向き)。

色・座標・Box の組み方はどのサンプルにも出てこない。出てくるのは意味役割名
(`support` / `conditional` / `none` / `danger` / `risk`)だけ。

## 案A: TeX 風の独自記法

````tex
\deck[template=light]{ランタイム移行計画}
\subtitle{ボード世代ごとの選択肢と期限}
\author{Boxloom デモ}

\begin{slide}{論点}
  \begin{points}
    \item 第1世代(Board A)は \emph{2029年12月} にハードウェア保守が切れる
    \item Loom 4 は Store X 非対応のため、第1世代は移行先になり得ない
    \item 第2世代以降は Loom 継続と Weft OS 移行の両方が選べる
  \end{points}
  \begin{compare}
    \option{Loom 継続}
      \pro{既存の運用手順をそのまま使える}
      \con{定額料金が 28/5・31/5 に更新}
    \option{Weft OS 移行}
      \pro{OS 25 で 2034年11月まで延ばせる}
      \con{移行期間の確保が要る}
  \end{compare}
  \note{期日はすべてイメージ}
\end{slide}

\begin{slide}{ランタイム選択肢と利用可能期間}
  \begin{gantt}[span=2026-09..2034-11]
    \tick{2029-12}{Board A・Store X}[status=danger]
    \milestone{2028-05}{ライセンス更新}
    \legend{support}{ランタイム サポート有}
    \legend{none}{ランタイム サポート無}
    \legend{risk}{ハードウェア サポート無}
    \begin{group}{第1世代 \\ Board A \\ 120台 \\ Store X}[risk=2029-12..2031-02]
      \row{Loom 2}[sub=固定版]
        \seg{2026-09}{2029-12}[status=none]{内部利用のみ、外部保守}
      \row{Loom 3}[sub=固定版]
        \seg{2026-09}{2028-08}[status=support]{内部+外部利用}
        \seg{2028-08}{2029-12}[status=conditional]{延長要確認}
    \end{group}
    \annotate{2029-12}[down, emphasis, status=danger]{ここまでに全利用者を Board B/C へ移行予定}
  \end{gantt}
\end{slide}
````

- **良い点**: 構想の「TeX 的に書く」にいちばん近い。本文と構造が混ざっても
  読める。マクロ(ユーザー定義の命令)の考え方とテンプレートの「部品」が素直に
  対応する。
- **悪い点**: パーサーを一から作ることになる。`%` `&` `_` `#` `\` などの
  エスケープが要り、日本語の本文でも `100%` のような文字で事故が起きる。
  Gantt のような構造の多いデータは命令の羅列になって読みにくい。`\seg` の
  引数の順番を覚える必要がある。

## 案B: Markdown + ディレクティブ(サブシステムは YAML の囲み)

本文は Markdown、意味ブロックは `:::名前` の囲み(MyST や Pandoc の
fenced div に近い)、サブシステムは言語名つきのコードブロックの中に YAML で書く。
`#` 見出しが1枚のスライドの始まりになる。

````markdown
---
title: ランタイム移行計画
subtitle: ボード世代ごとの選択肢と期限
author: Boxloom デモ
template: light
---

# 論点

- 第1世代(Board A)は **2029年12月** にハードウェア保守が切れる
- Loom 4 は Store X 非対応のため、第1世代は移行先になり得ない
- 第2世代以降は Loom 継続と Weft OS 移行の両方が選べる

::::compare
:::option Loom 継続
+ 既存の運用手順をそのまま使える
- 定額料金が 28/5・31/5 に更新
:::
:::option Weft OS 移行
+ OS 25 で 2034年11月まで延ばせる
- 移行期間の確保が要る
:::
::::

:::note
期日はすべてイメージ
:::

# ランタイム選択肢と利用可能期間

```gantt
span: 2026-09 .. 2034-11
ticks:
  - {at: 2029-12, label: Board A・Store X, status: danger}
milestones:
  - {at: 2028-05, label: ライセンス更新}
legend:
  support: ランタイム サポート有
  none: ランタイム サポート無
  risk: ハードウェア サポート無
groups:
  - label: [第1世代, Board A, 120台, Store X]
    risk: 2029-12 .. 2031-02
    rows:
      - label: Loom 2
        sub: 固定版
        segments:
          - {from: 2026-09, to: 2029-12, status: none, label: 内部利用のみ、外部保守}
      - label: Loom 3
        sub: 固定版
        segments:
          - {from: 2026-09, to: 2028-08, status: support, label: 内部+外部利用}
          - {from: 2028-08, to: 2029-12, status: conditional, label: 延長要確認}
annotations:
  - {at: 2029-12, text: ここまでに全利用者を Board B/C へ移行予定, status: danger, direction: down, emphasis: true}
```
````

- **良い点**: 文章の多いスライドがいちばん楽に書ける。ふだんのメモや README の
  延長で書け、GitHub などでそのまま読める。構造の多いデータは YAML に逃がせる
  ので、本文と表データでそれぞれ向いた書き方ができる。サブシステムごとに囲みの
  中の書き方を決められ、サブシステムを足しても本体の記法は変わらない。
- **悪い点**: 1つのファイルに2つの記法(Markdown と YAML)が混ざる。
  Markdown には「比較」「良い点/悪い点」のような意味の型が無いので、約束事を
  足すことになる(上の `+` / `-` は CommonMark では「別のリストの始まり」として
  区別できるが、気づきにくい)。`#` の段数とスライドの区切りの対応も決める必要が
  ある。

## 案C: YAML(全部を構造化データで)

````yaml
deck:
  title: ランタイム移行計画
  subtitle: ボード世代ごとの選択肢と期限
  author: Boxloom デモ
  template: light

slides:
  - title: 論点
    body:
      - points:
          - "第1世代(Board A)は **2029年12月** にハードウェア保守が切れる"
          - Loom 4 は Store X 非対応のため、第1世代は移行先になり得ない
          - 第2世代以降は Loom 継続と Weft OS 移行の両方が選べる
      - compare:
          - option: Loom 継続
            pros: [既存の運用手順をそのまま使える]
            cons: [定額料金が 28/5・31/5 に更新]
          - option: Weft OS 移行
            pros: [OS 25 で 2034年11月まで延ばせる]
            cons: [移行期間の確保が要る]
      - note: 期日はすべてイメージ

  - title: ランタイム選択肢と利用可能期間
    body:
      - gantt:
          span: 2026-09 .. 2034-11
          ticks:
            - {at: 2029-12, label: Board A・Store X, status: danger}
          milestones:
            - {at: 2028-05, label: ライセンス更新}
          legend:
            support: ランタイム サポート有
            none: ランタイム サポート無
            risk: ハードウェア サポート無
          groups:
            - label: [第1世代, Board A, 120台, Store X]
              risk: 2029-12 .. 2031-02
              rows:
                - label: Loom 2
                  sub: 固定版
                  segments:
                    - {from: 2026-09, to: 2029-12, status: none, label: 内部利用のみ、外部保守}
                - label: Loom 3
                  sub: 固定版
                  segments:
                    - {from: 2026-09, to: 2028-08, status: support, label: 内部+外部利用}
                    - {from: 2028-08, to: 2029-12, status: conditional, label: 延長要確認}
          annotations:
            - {at: 2029-12, text: ここまでに全利用者を Board B/C へ移行予定, status: danger, direction: down, emphasis: true}
````

- **良い点**: IR とほぼ1対1で、JSON Schema でそのまま検査できる。知らない
  キー(`color:` など)を「不正」として断れるので、意味とデザインの分離を
  機械的に守らせやすい。プログラムから生成・変換するのも簡単。
- **悪い点**: 文章が多いスライドは窮屈。強調などの文中の装飾には結局小さな
  マークアップ(上の `**…**`)が要る。字下げを間違えると意味が変わる。YAML の
  落とし穴がある: `*` や `&` で始まる値は別の意味(参照)になるので引用符が要る、
  `{…}` の中で半角の `,` を本文に書くと区切りと誤解される、`no` / `on` が
  真偽値になる処理系がある、`2026-09-01` のような完全な日付は日付型に化ける。

## 案D: Go の DSL(関数呼び出しで組む)

````go
package deck

import (
	. "boxloom/content"
	g "boxloom/content/gantt"
)

var Deck = Doc(
	Meta(Title("ランタイム移行計画"),
		Subtitle("ボード世代ごとの選択肢と期限"),
		Author("Boxloom デモ")),

	Slide("論点",
		Points(
			P("第1世代(Board A)は ", Em("2029年12月"), " にハードウェア保守が切れる"),
			P("Loom 4 は Store X 非対応のため、第1世代は移行先になり得ない"),
			P("第2世代以降は Loom 継続と Weft OS 移行の両方が選べる"),
		),
		Compare(
			Option("Loom 継続",
				Pro("既存の運用手順をそのまま使える"),
				Con("定額料金が 28/5・31/5 に更新")),
			Option("Weft OS 移行",
				Pro("OS 25 で 2034年11月まで延ばせる"),
				Con("移行期間の確保が要る")),
		),
		Note("期日はすべてイメージ"),
	),

	Slide("ランタイム選択肢と利用可能期間",
		g.Chart(g.Span(g.YM(2026, 9), g.YM(2034, 11)),
			g.Tick(g.YM(2029, 12), "Board A・Store X", g.Danger),
			g.Milestone(g.YM(2028, 5), "ライセンス更新"),
			g.Legend(g.Support, "ランタイム サポート有"),
			g.Legend(g.None, "ランタイム サポート無"),
			g.Legend(g.Risk, "ハードウェア サポート無"),
			g.Group(g.Lines("第1世代", "Board A", "120台", "Store X"),
				g.RiskBand(g.YM(2029, 12), g.YM(2031, 2)),
				g.Row("Loom 2", g.Sub("固定版"),
					g.Seg(g.YM(2026, 9), g.YM(2029, 12), g.None, "内部利用のみ、外部保守")),
				g.Row("Loom 3", g.Sub("固定版"),
					g.Seg(g.YM(2026, 9), g.YM(2028, 8), g.Support, "内部+外部利用"),
					g.Seg(g.YM(2028, 8), g.YM(2029, 12), g.Conditional, "延長要確認")),
			),
			g.Annotate(g.YM(2029, 12), "ここまでに全利用者を Board B/C へ移行予定",
				g.Danger, g.Down, g.Emphasis),
		),
	),
)
````

- **良い点**: 型で検査される。状態の名前の打ち間違い(`g.Suport`)はコンパイル
  で落ちる。エディタの補完が効く。ループや関数で繰り返しを減らせる。
- **悪い点**: 作者に Go のツールチェーンが要る。これは「Python を入れにくい PC でも単一の
  バイナリで動く」という Go 版の利点を、作者の側で打ち消してしまう。本文が
  文字列リテラルに閉じ込められ、強調ひとつでも `P(…, Em(…), …)` と書く。任意の
  コードが書けるので、作者が見た目をいじる道も開いてしまう(分離が規約頼みに
  なる)。**作者向けよりも、テンプレート・プラグインの開発者向け、および試験用**
  に向いている。

## その他の候補(サンプルは省略)

- **Typst 風**: TeX より現代的で、文中のマークアップも軽い。ただ AI の学習
  データが少なく、独自の方言にするとさらに少なくなる。
- **XML / JSX 風のタグ**: 構造は明確で検査しやすいが、人が書くには重い。
- **KDL / TOML**: 構造化データとしては YAML より落とし穴が少ないが、
  知っている人(と AI)が少ない。TOML は深い入れ子が苦手で Gantt に向かない。
- **IR(JSON)を直接**: 人は書かない前提。AI の構造化出力(JSON Schema に従う
  出力)の宛先としては最も確実。

## AI が扱いやすいか

AI(LLM)が書く・直す相手としての評価。観点は次の6つ。

1. **知っているか**: 学習データにその記法がどれだけあるか。
2. **壊さずに書けるか**: 括弧の対応・字下げ・引用符などの事故の起きやすさ。
3. **方言に引きずられないか**: よく似た既存の記法の命令を勝手に混ぜないか。
4. **誤りを直せるか**: 検査の結果を AI に返したとき、直す場所が一意に分かるか。
5. **部分的に直しやすいか**: 1か所だけを差し替える編集(文字列の置き換え)が
   安全にできるか。
6. **トークン数**: 同じ内容を書くのに要る量。

### A: TeX 風 —— 知ってはいるが、本物の LaTeX に引きずられる

- 知っているか: LaTeX はよく知っている。ただしそれが裏目に出る。
- 方言: **いちばん危ない**。AI は `\textbf` `\vspace{1em}` `\centering`
  `\textcolor{red}{…}` のような本物の LaTeX の命令を自然に書き足す。これらは
  まさにコンテンツに入ってほしくない「見た目の指定」で、しかも書いた本人
  (AI)には正しく見える。
- 壊さずに書けるか: `\begin` と `\end` の対応は概ね守れるが、`%` `&` `_` の
  エスケープ漏れはよく起きる。
- 誤りを直せるか: 自前のパーサーの出す誤りの文次第。
- トークン数: 中くらい。`\seg{…}{…}[…]{…}` の命令名と括弧が多い。

### B: Markdown+ディレクティブ —— 最も自然に書くが、約束事は忘れやすい

- 知っているか: Markdown は最もよく知っている記法。YAML も同じくらい知っている。
  `:::` の囲みは MyST / Pandoc / Docusaurus にあり、そこそこ知っている。
- 壊さずに書けるか: 本文はほぼ壊れない。`::::` と `:::` の入れ子の数の
  対応はたまに崩れる。
- 方言: AI は GitHub 風の Markdown に寄せがちで、生の HTML(`<br>`
  `<span style=…>`)や、`> [!NOTE]` のような別の方言の注記を混ぜることがある。
  `+` / `-` で良い点・悪い点を分けるような **見た目では区別しにくい約束事は
  忘れやすい**。約束事は「名前で書く」形(`:::pro` のような)にしたほうが
  AI には安全。
- 誤りを直せるか: Markdown は「何でも何かしらとして通る」ので、誤りが誤りとして
  出にくい(意図と違う解釈で黙って通る)。囲みの中の YAML は Schema で検査でき、
  場所も示せる。
- 部分的に直しやすいか: 1行1項目なので置き換えやすい。
- トークン数: 最も少ない。

### C: YAML —— 構造化出力の宛先として最も確実、文章は苦手

- 知っているか: よく知っている。
- 壊さずに書けるか: 字下げはほぼ守れる。事故が多いのは引用符で、`*` や `:`
  を含む値の引用符漏れ、`{…}` の中の半角 `,`。
- 方言: 起きにくい。代わりに `color: red` や `align: center` のような
  **キーを勝手に足す** ことがあるが、Schema で知らないキーを断れば、誤りとして
  確実に返せる。
- 誤りを直せるか: **最も直しやすい**。JSON Schema の誤りは「どの場所の、
  どのキーが、何であるべきか」まで言えるので、AI はほぼ一度で直せる。
  JSON Schema を AI にそのまま渡して、構造化出力として書かせることもできる。
- 部分的に直しやすいか: 同じ形の行が並ぶので、置き換えの対象が一意に
  決まらないことがある(`sub: 固定版` がいくつもある、など)。
- トークン数: 多い(キー名を毎回書く)。

### D: Go DSL —— 型の検査は強いが、作者の道具としては重い

- 知っているか: Go はよく知っている。
- 壊さずに書けるか: 括弧と `,` の対応で落ちることはあるが、コンパイラが
  すぐに場所を示す。
- 方言: 任意のコードが書けるので、AI は「便利だから」と見た目を直接触る
  関数を呼んだり、新しい関数を定義したりしがち。`content` パッケージから
  見た目の API を一切出さないことで、ある程度は防げる。
- 誤りを直せるか: コンパイルの誤りの文は正確で、直しやすい。ただし AI に
  Go のビルドを回させる環境が要る。
- トークン数: 多い。

### AI にとっては記法より「検査の口」のほうが効く

どの記法を選んでも、AI が上手く書けるかどうかは、**誤りを機械で返せるか** で
ほぼ決まる。記法とは別に、次を用意するのがよい。

- `boxloom check` のような検査のコマンド。誤りを「ファイル・行・IR の中の場所・
  期待したもの・直し方の候補」の形で、機械が読める形式(JSON)で返す。
- IR の JSON Schema を書き出すコマンド。AI に渡せば、書く前から形が分かる。
- レイアウトの検査(はみ出し・fill-ratio など、テンプレートの規則)の結果も
  同じ形式で返す。AI は「文字が多すぎて枠からはみ出した」を受け取って、
  文章を削る判断ができる。

## 決定

記法は **案B を厳格にしたもの(Boxloom Markdown)を主な入口** とし、IR の写し(C)を
併存させる。D は開発者・試験用、A は採らない。仕様は `docs/content-syntax.md`。

案B からの主な変更は、弱点を塞ぐための次の2点。

- **約束事は記号ではなく名前で書く**(良い点・悪い点は `+`/`-` ではなく `:::pros`/`:::cons`)。
- **意味が決まらない書き方は誤りにする**(知らない囲み・属性、生の HTML、別の方言の構文)。
  誤りは `boxloom check` が場所つきの JSON で返す。
