# 組みの三段:意味からレイアウトまでの分け方

**状態:方向は決まった(三段に分ける・作者は意味だけ・標準の部品と代わりの組み方・
部品はまず Go で登録)。8章はすべて決まった(8.1〜8.3)。** 7章の1〜4段目は済み
(#62〜#65・#68)、その後に `layout-input`(#69)。

意味のブロック(IR)をレイアウトの木に組む仕事を、3つの段に分ける。
狙いは、新しい内容の型(下の「対の並び」など)を足すたびに `buildBlockSpec` の
switch を太らせるのをやめ、型の**組み方**をテンプレートの側でも持てるように
することである。型の**意味**(名前と欄)はテンプレートに依らず1つに保つ(8.2)。

## 0. 名前の整理

Boxloom にはすでに「三層」が2つある。ここで書くのはそのどちらとも別の切り方なので、
**「段」**と呼んで区別する。

| 呼び名 | どこに書いてある | 何を分けるか |
|---|---|---|
| 三層の分離 | CLAUDE.md | コア(仕組み)/テンプレート(方針)/コンテンツ(意味)の**持ち主** |
| 3層の構想 | docs/vision.md の3章 | スライドのパターン/キャンバス/キャンバスの中の図の**語彙** |
| 組みの三段(この文書) | docs/layers.md | 意味をレイアウトに組む**変換の段階** |

組みの三段は、三層の分離の「テンプレート(方針)」のうち、いまコードで書いている
「意味ブロックを Box の部分木に組む部品」を切り出して、仕組みを与えるものである。
作者(AI)が書くコンテンツの層は変わらない。

## 1. なぜ要るか

外の資料(コンサルティングの報告書の型)を Boxloom で書けるか調べたところ、
いちばん多く足りなかったのは次の型だった。

- **対の並び**:左に「分かったこと」、右にそれを受けた「打ち手」や「根拠」を置き、
  左右の行の高さをそろえて何組も縦に並べる。左右それぞれの中に箇条や引用が入る。

  (例・架空)
  | 分かったこと | 打ち手 |
  |---|---|
  | 平日の午後に客が減る | 午後だけの焼きたての品を出す |
  | 常連の半分は徒歩10分の外から来る | 駐輪場を広げる |

いまの作りでこれを足すと、次のことが全部コアの仕事になる。

1. IR の Schema(schema/)に `pairs` の型を足す。
2. Markdown の読み取り(md_blocks.go)に囲みを足す。
3. `buildBlockSpec` の switch に組み方を足す。
4. 容量の計測・はみ出しの警告が、その型の中のどこを1単位として測るかを
   コアの非公開の欄(`columns`・`cards` など)で教える。

型の数だけこれを繰り返すと、コアが「どんな型があるか」と「それをどう組むか」の
両方を抱え込む。テンプレートは値の表とサブシステムの描き方は差し替えられるのに、
ブロックの組み方は差し替えも追加もできない。ここが今回の問題である。

## 2. 三段

```
 作者(AI)が書く        テンプレートの段:どの部品を使うか・値の表
  意味(IR)  ──▶  部品の段  ──▶  配置の段  ──▶  レイアウトエンジン ──▶ PPTX
                  (意味→箱の木)   (箱の木:Row/Col/文字/葉)
```

### 2.1 配置の段(レイアウトの入力)

いまの `Spec` にあたる。Row・Col を入れ子にした箱の木で、葉は文字・箇条・
カード・サブシステム。**持つのはトークンだけ**とする。

- 間隔・余白は値の表の名前(`blockGap`・`cardPadding` …)か、刻み(scale の
  spacingUnit の倍数。例 `space(5)`)。
- 字の大きさは値の表の名前(`body`・`subPoint` …)か、字の段(typeSizes。例 `type(14)`)。
- 色は役割名(`accent`・`text_muted` …)だけ。16進の色は書けない。
- 幅の分け方は grow・basis の比で書く(比はトークンにせず、ただの数)。
- 段に無い数は書けない。標準の部品は名前だけで書く(刻み・段は、足す部品・
  テンプレートの組み方・木の入力の逃げ道)。8.3 の3つ目。
- **座標は持たない。** 位置はレイアウトエンジンが決める。

`Spec` は Go の中だけの型で、部品はトークン(`tokGap("blockGap")`・`tokSize("body")`・
`tokBackground("card")`・塊の `role` など。`boxloom/token.go`)を書き、解決は組み立ての
直後・計測の前の1か所(`BuildSlide` の中の `resolveSpec`)でする(8.3 の4つ目。**済み**、
#68)。組み方の中で値の表から外れた数を書けない(#1301886 の段の検査が組み方にも効く):
トークンの無い数・色、段に無い刻み、知らない名前・役割名は組み立ての誤り。
標準の部品と骨組みが名前だけを書くことは `TestStandardComponentsWriteNamesOnly`
(`boxloom/token_test.go`)が examples の全 deck × dark・light・forest で確かめる。
`itemGap` の半分のような計算した値は名前にならないので、値の表に名前を足した
(区切りの章の一覧の余白 `sectionTrackerPadding`)。入れ子の箇条の字下げは
em の名前 `pointIndentEm` を空きの箱の字の大きさ(`body`・`subPoint`)に掛ける。
表・画像の葉の中(セルの字・説明の文)はサブシステムと同じくトークンの外で、
これまでどおり組み立てのときに値を引く。

計測の印もこの段の語彙にする。いまは非公開の欄で持っている。

| いまの欄 | 意味 | 配置の段での形(案) |
|---|---|---|
| `irType` | はみ出しの警告に出すブロックの種類 | 部品の段が付ける(作者の IR の場所) |
| `columns` | まとまりごとにはみ出しを測る | 「測る単位」の印 |
| `cards` | カードごとの高さを容量に出す | 「測る単位」の印(並びの名前つき) |
| `pairs` | 対(行)ごとにはみ出しを測り、容量に側ごとの高さを出す(#65 で足した) | 「測る単位」の印(`measurePairRows`) |
| `keepLine` | 1行に収めたい文字 | 文字の葉の属性 |
| `nestedSlack` | 中の図を文字より先に縮める | 箱の属性 |
| `List`・`card` | PPTX で1つの図形・段落にまとめて書く | 箱の種類(箇条・カード) |

これで、部品を足した人も、コアに手を入れずに容量の計測とはみ出しの警告を
受けられる。

### 2.2 部品の段(意味 → 箱の木)

IR の1ブロックを受け取り、配置の段の木を返す。いまの `points`・`compare`・
`stat`・`columns`・`table` などの関数がこれにあたる。

部品は2つに分けて名乗る(8.2)。

**型の語彙**(プロセスに1つ。どのテンプレートでも同じ):

- **名前**:IR の `type` の値。意味の名前にする(`pairs` であって `two-col-grid`
  ではない)。
- **意味の形**:IR の Schema の断片(その型が持つ欄)。サブシステムの
  `SubsystemDecl{Schema, Markdown}` と同じやり方。
- **Markdown の囲み**:`BlockDecl`(いまの `Template.Blocks` と同じもの)。
- **代わりの組み方**:標準でない型だけ(5章)。IR → 標準の型の IR。

**組み方**(テンプレートごと):IR のブロック → 配置の段の木。

サブシステムとの違い:サブシステムは渡された矩形の中を自分で描く(中の座標は
サブシステムが持つ)。部品は箱の木に**展開される**だけで、自分では描かない。
そのため、展開された中身は文字の計測・折り返し・はみ出しの警告・PowerPoint の
機能で書く文字(#1301889)をそのまま受ける。
対の並びは「行をそろえる」だけで位置そのものに意味は無いので、サブシステムでなく
部品にする(#1272978 の線引きのとおり)。

### 2.3 テンプレートの段

いまの値の表(templates/<名前>.json)に加えて、部品について次のことができる。

- **差し替える**:標準の型の組み方を、テンプレートが自分のものに替える
  (サブシステムの `Override` と同じ。名前と意味の形は替えられない)。
- **組み方を持つ**:語彙にある標準でない型(`pairs` など)の組み方を持つ。
  持たない型は代わりの組み方で組まれる。
- **できないこと**:新しい意味(語彙に無い型・欄)を作ること。型を足すのは語彙の側
  (コア、のちにはプロセスに登録するライブラリの使い手)の仕事で、テンプレートは
  その組み方を持つだけである(8.2)。
- 骨組み(表紙・本文・区切り)は今回の範囲の外。同じ形で後から部品にできる。

## 3. 境目

| 段 | 持つもの | 持たないもの | 書く人 |
|---|---|---|---|
| 意味(IR) | 型の名前と意味の欄 | 箱の組み方・値・色・座標 | 作者(AI) |
| 型の語彙 | 名前・意味の形・囲み・代わりの組み方 | 組み方・値・座標 | コア(プロセスに1つ) |
| 部品の段 | 意味→箱の木(組み方) | 意味の形、実際の pt・色の値、座標 | コア(標準)・テンプレート(差し替え・標準でない型) |
| テンプレートの段 | どの型の組み方を持つか・差し替え、値の表 | コンテンツ、新しい意味 | テンプレートの作者 |
| 配置の段 | 箱の木、トークン、計測の印 | 意味、座標 | 部品が作る |
| エンジン(コア) | 配置・計測・PPTX の書き出し | どんな型があるか | コア |

コアに残るのは「箱の木を置いて測って書き出す仕組み」と「標準の部品」だけになる。

## 4. 作者に書かせるのは意味の層だけ

段が増えても、作者(AI)の書くものは変えない。

- IR とその Markdown は意味だけを持つ(#1279989)。配置の段の木を IR に書く口は
  作らない。部品の引数として幅・色・並べ方を受け取ることもしない。
- 部品の名前と欄は意味で選ぶ。「左右に置く」ではなく「分かったことと打ち手の対」。
- 生の図形への逃げ道は、これまでどおりキャンバス(`shapes`)の中だけ(#1269030)。
  配置の段は逃げ道にしない。
- 配置の段の木は JSON で**出せる**(`boxloom layout`、#67。**済み**)。なぜその大きさ・はみ出しに
  なったかを人と AI が読むためのものである。形は `schema/layout.schema.json`、出し方は
  `docs/build.md` の「配置の段の木を見る」。いまの木は値を持つので、トークンの名前は
  値から1つに決まるときだけ添える。
- その木を**入力として読む口**は、開発者・試験用に限る(Go DSL と同じ立ち位置。
  エンジンだけを試す・崩れた例を木のまま再現する)。`boxloom schema` の出力や
  SKILL.md など作者向けのものには載せない。作るのは配置の段をトークンのまま
  持つ形(7章の4段目)の後で、読むときに間隔・余白・字の大きさ・色が値の表の名前か
  段(scale)に載っているかを検査する(#69)。値が固まったいまの木を読めるように
  すると、段の検査とテンプレートの差し替えを素通りするため。
- `boxloom schema` は語彙の型すべての意味の形と囲みを出す。`-template 名前` を
  付けると、型ごとにそのテンプレートが組み方を持つか(持たなければ代わりの組み方で
  組まれる)を添える。型を隠しはしない。作者はそこから選ぶ。

## 5. 標準の部品と代わりの組み方

型の組み方がテンプレートごとにあると、**コンテンツが特定のテンプレートに
縛られる**おそれがある(`pairs` を使った文書が、`pairs` の組み方を持たない
テンプレートで組めない)。これを2つで防ぐ。

1. **標準の部品**:どのテンプレートも必ず組める部品の一式。いまのコアの
   ブロック(paragraph・note・points・compare・stat・takeaway・quote・
   columns・table・image・gallery・subsystem)がこれにあたる。テンプレートは
   組み方を差し替えられるが、外せない。
2. **代わりの組み方**:標準でない型は、語彙に自分の IR を**標準の型の IR に
   書き換える関数**を必ず持つ。テンプレートがその型の組み方を持たなければ、
   代わりの組み方で組み、check と build が警告 `component-fallback` を出す。

   (例)`pairs` の代わり:左右2つのまとまりの `columns`。左右の見出しは
   まとまりの題に、各対の左右の中身はそれぞれのまとまりに順に入れる。
   行は左右でそろわなくなるが、読める。

代わりの組み方は IR → IR なので、その結果はコアの Schema と check でそのまま
確かめられる。部品を足した人が代わりの組み方を誤れば、試験で分かる。

標準の部品の一覧そのものは小さく保つ。新しい型は、まず標準でない型として
(代わりの組み方つきで)語彙に足し、多くのテンプレートが組み方を持つように
なったら標準に上げる。

## 6. 部品はまず Go で登録する

部品を値の表のようにデータ(JSON)で書けるようにすると、「繰り返し」「条件」
「欄を取り出す」などの小さな言語が要る。何が要るかはまだ分からない。そこで、
**まず Go で登録し、作った部品が揃ってから、データで書ける形を考える。**

登録は、型の語彙(プロセスに1つ)と組み方(テンプレートごと)の2つに分ける(案)。

```go
// 型の語彙。プロセスに1つ。
type TypeDecl struct {
	Schema   json.RawMessage // IR の意味の形(Schema の断片)
	Markdown BlockDecl       // 囲み
	// Fallback は標準でない型だけ。標準の型の IR に書き換える。
	Fallback func(b *IRBlock) ([]*IRBlock, error)
}
func RegisterType(name string, d TypeDecl) error

// 組み方。テンプレートごと。
type Component interface {
	// Build は IR のブロックから配置の段の木を作る。
	Build(ctx ComponentContext, b *IRBlock) (*Spec, error)
}
type ComponentRegistry struct{ /* 型の名前 → Component */ }
func (r *ComponentRegistry) Register(name string, c Component) error // 標準でない型の組み方
func (r *ComponentRegistry) Override(name string, c Component) error // 標準の差し替え
```

`ComponentRegistry` に登録できるのは語彙にある型だけである。

`ComponentContext` は値の表・役割名・入れ子の部品を組む口(`columns` の中の
箇条など)を渡す。

## 7. 移し方(案)

1. **いまの組み方を登録簿に移す。** `buildBlockSpec` の switch を登録簿の
   引き方に替え、標準の部品を登録する。出力は1バイトも変えない(例の deck の
   PPTX と check の JSON が同じであることを試験で確かめる)。
   **済み(#62)。** `boxloom/component.go` の `componentRegistry`(register・
   override・clone。サブシステムの登録簿と同じ形)に標準の12の部品を登録し、
   `Template` はその写しを持つ。部品は `componentDecl{Schema, Markdown}` を名乗る
   (標準の部品は Schema を IR の Schema に任せて空、Markdown は `defaultBlocks` の
   囲みをそのまま分け持つ)。代わりの組み方(fallback)は interface にあるだけで、
   標準の部品は持たない。当面は package の中だけの名前で、公開 API は増やしていない。
   出力が変わらないことは `TestOutputsGolden`(examples の全 deck の build の PPTX の
   部品ごと・check の JSON・schema を記録した sha256 と比べる。
   `boxloom/testdata/outputs-golden.json`)で確かめる。
2. **計測の印を公開の語彙にする**(2.1 の表)。これも出力は変えない。
   **済み(#63)。** 印は `boxloom/layout.go` の `SpecOpt` の語彙になった:
   `markIRType`(はみ出しの警告に出す IR の種類)、測る単位の `measureColumnGroups`
   (columns のまとまり)・`measureCardRow`(カードの並び。IR の並びの名前つき)、
   文字の葉の `keepLine`、箱の属性の `nestedSlack`、箱の種類の `asList`・`asCard`。
   標準の部品はこの語彙だけで印を付け、overflow.go・capacity.go・keepline.go・
   pptx の書き出しは印を読むだけ(`TestMarksOnlyThroughVocabulary` が layout.go の外で
   欄に直接書いていないことを確かめる)。当面は package の中だけで、公開はしていない。
   出力が変わらないことは `TestOutputsGolden` で確かめる(記録は変えていない)。
3. **最初の追加の部品として `pairs` を作る。** 標準でない型として語彙に足し
   (代わりの組み方は `columns`)、組み方は dark・light が持つ(8.1)。
   **`pairs` は済み(#65)。** `boxloom/pairs.go`:型の宣言(Schema は
   `schema/types/pairs.schema.json`。コアの `block` の振り分けもそこを指すので、
   `tools/validate_ir.py` も読める)・IR の形の検査(`typeDecl.Validate`)・Markdown の読み方
   (`typeDecl.readMarkdown`。8.3)・代わりの組み方・組み方。組み方は同梱のテンプレート
   (`templates/*.json`。いまは dark・light)が読み込みのときに持ち(`registerBundledComponents`)、
   外の値の表だけのテンプレート(`ParseTemplate`、例 `examples/templates/forest.json`)は
   持たない(代わりの `columns` で組み、`component-fallback`)。対ごとに1つの行(2つの側は
   同じ幅・交差軸は STRETCH)にするので、2つの側の上端がそろい、行の高さは高い方になる。
   はみ出しは測る単位の印 `measurePairRows` で対ごとに測る(2.1 の表)。例は
   `examples/md/pairs.bx.md`、代わりの組み方の IR は `examples/ir/pairs-fallback.json`、
   試験は `boxloom/pairs_test.go`。
   Backlog の `type-vocabulary`(#64。語彙と組み方を分ける)と `pairs-component`(#65)。
   **語彙と組み方を分けるのは済み(#64)。** 型の語彙は `boxloom/typevocab.go` の
   `blockTypes`(`typeDecl{Schema, Markdown, Fallback}`。標準の12の型は Fallback を
   持たない。標準でない型は `registerType` で足し、Schema と Fallback が必須)。
   `componentRegistry` は組み方だけを持ち、登録できるのは語彙にある型だけ
   (標準の型は `override`、標準でない型は `register`)。組み方の無い標準でない型は
   Fallback で標準の型に書き換えて組み、警告 `component-fallback` を出す(path はその
   ブロック)。`check` はテンプレートを指したときだけこの警告を足す。`schema` の
   `templates[].types` に型ごとの組み方(`template`・`fallback`)が出る。型ごとの
   Schema は `schema/types/<名前>.schema.json`。公開 API は増やしていない。
   試験用の標準でない型で確かめる(`component_test.go`)。
4. 配置の段をトークンのまま持つ形(値を後で解決する)に替える。Backlog の
   `token-spec`(#68)。**済み**(2.1。`boxloom/token.go`)。その後で、木を入力として読む口(`layout-input`、#69。
   開発者・試験用、4章)を作る。木を出す口(`layout-dump`、#67)は**済み**(`boxloom layout`。箱・印・値・決まった座標を
   出す。`boxloom/layoutdump.go`。部品が書いたトークンを `tokens` に出す)。
5. 部品が数個そろったら、データで書ける部品を考える。

1・2 は外から見える振る舞いを変えないので、先にやってよい。3 以降は決めてから。

## 8. 決めたこと

### 8.1 `pairs` の置き場(決めた)

`pairs` は標準の部品にしない。足す部品の最初の1つにする。外の資料では最も多い型
だったが、発表用のスライドでは少ないため、標準の一覧を小さく保つ(5章)。

- 意味の形:左右の見出し(列の題)を1回だけ書き、そのあとに対を並べる。
  対の左右はそれぞれ段落・箇条・引用のどれか。
- 代わりの組み方は `columns`(5章の例)。
- 組み方は dark・light が持つ。左右の行をそろえる(対ごとに左右の高い方に合わせる)。

### 8.2 IR の Schema はテンプレートで変えない(決めた)

IR の Schema はテンプレートに依らず1つ。型の語彙(名前・意味の形・囲み・
代わりの組み方)はプロセスに1つ持ち、テンプレートごとに持つのは組み方だけ。

- 知らない type はこれまでどおり誤り(#1251081)。語彙にある型は、テンプレートが
  組み方を持たなくても誤りでない。
- `check` はテンプレートを指さなければ語彙だけで検査する。指せば、そのテンプレートが
  組み方を持たない型に `component-fallback` の警告を足す。
- `schema -template` は型を隠さず、型ごとに組み方を持つか・代わりで組むかを添える。
- 型ごとの Schema は schema/ に型ごとのファイルで置く(例 `pairs.schema.json`)。
  サブシステムと同じく正本は schema/、Go は写しを埋め込む。
- このため 2.3 のとおり、テンプレートは新しい意味を作れない。

### 8.3 決めたこと

はじめの2つは `pairs` を作る中で決めた(#65)。あとの2つは #68 の前に決めた。

- **Markdown の囲みを `BlockDecl` から一般に読めるか(決めた:読まない)。** `BlockDecl` は
  名乗り(名前・見出しの文の意味・置き場所 `Inside`・中に書けるもの・属性)だけで、
  中身から意味の欄への写し方は型ごとの読み方(Go の関数。`typeDecl.readMarkdown`)が持つ。
  `pairs` の「`:::subject` と `:::response` を交互に書いて1組」「見出しを `|` で2つに分ける」
  のような約束事は、宣言の小さな言語で書くより、コードで書いて場所つきの誤りを返すほうが
  読みやすく、6章の「まずコードで」と同じ理由で、データで書く形は部品がそろってから考える。
  パーサーの側は一般にした:本文に置いた囲みの名前が語彙の型の(本文に置く)囲みなら
  その読み方を呼び、ほかの囲みの中だけの囲み(`Inside` を持つもの)を本文に書けば
  宣言から誤りの文を作る。受け付ける囲みの一覧(誤りの `expected`)と `boxloom schema` の
  `blocks` も語彙から作る(テンプレートは型を隠さないので、どのテンプレートも語彙の
  すべての囲みを名乗る)。
- **ライブラリの API の広さ(決めた:当面は増やさない)。** 型の語彙(`registerType`・
  `typeDecl`)・部品の登録簿(`componentRegistry`)・`Spec` と計測の印は package の中だけ。
  外から見えるのは、これまでの入口(`ParseMarkdown`・`ReadDeck`・`Check`・`Build`・`Schema`
  など)が `pairs` を読み・検査し・組むことと、`schema` の出力・容量(`BlockCapacity.Pairs`・
  `PairCapacity`)・layout の印(`LayoutMarks.PairRows`)だけ。部品を外から足せるように
  するのは、`Spec` がトークンを持つ形(7章の4段目、#68)にしてからにする(いま公開すると、
  値の決まった pt の木が安定させる API になり、段の検査を素通りする口になるため)。
- **配置の段で、値の表に無い数を許すか(決めた:名前と段の刻みだけ)。** 書けるのは
  値の表の名前と、段の上の刻み(余白は spacingUnit の倍数、字は typeSizes の段)だけ。
  段に無い数は書けない(#1301886 の検査がそのまま効く)。標準の部品は名前だけで書く
  (試験で確かめる)。値の表を直せば全部に効くようにするため。刻み・段は、足す部品・
  テンプレートの組み方・木の入力(#69)の逃げ道として残す。名前だけにすると、部品が
  新しい間合いを欲しがるたびに値の表の名前が増えるため。色は役割名だけ(16進は
  書けない。キャンバスの #1269030 と同じ)。grow・basis の比はトークンにしない。
- **解決の時点とサブシステムへの渡し方(決めた)。** 組み方は `Spec` にトークンを書き、
  組み立ての直後・計測の前に1か所(`resolveSpec`、値の表を引く)で数と色に直す。
  計測・配置・PPTX の書き出しは解決した数を読むので、エンジンは変えない(エンジンが
  計測の中で名前を引く形は、名前の引き方がエンジン全体に入り込むので採らない)。
  サブシステムへの渡し方は今のまま:トークンはサブシステムの葉の外側(余白・置き方)で
  終わり、中の寸法はテンプレートを選んだ時に値の表(段の検査済み)から Factory に渡し、
  色は描く時に `Roles` で役割名から引く。`Roles` を余白・字の段にまで広げて Measure に
  渡す形は、interface が変わり要る理由も無いので採らない。サブシステムの中に直に
  書いた数は #68 の範囲の外で、Backlog の `subsystems-gantt`(#70)で値の表(見た目の
  寸法)と名前つきの定数(決まりの数)に分けた(`docs/subsystem.md` の13節)。
