# Boxloom の方向性

なぜ Boxloom を作るのか、何を作り何を作らないのか、いまどこまで来たのかを書く。
設計の結論は `CLAUDE.md`、経緯は `HANDOFF.md`、今後の仕事は Backlog(6つのストーリー)。

各節の終わりの **いま** は、この文書を書いた時点の実装の状態。変わったら書き直す。

## 1. 出発点:AI が作るスライドはなぜひどいのか

AI が作る PowerPoint の質の悪さは、原因の違う3つに分けられる。

1. **機械的な破綻** — 要素の重なり、文字のはみ出し、余白の不揃い。
2. **見た目の趣味の悪さ** — 配色、字の組み方、視覚的な階層の作り方。
3. **情報の密度と構成の判断の悪さ** — 1枚に詰め込みすぎる、または薄すぎる。

レイアウトエンジンが直接効くのは1つ目だけだが、これは小さい話ではない。言語モデルは
座標の手計算が本質的に苦手で、python-pptx などに x・y・幅・高さを直接書かせると
重なりやはみ出しが起きやすい。そのため AI は破綻を避けて、要素の少ない薄い
レイアウトに逃げる。**3つ目の「薄い」の一部は、1つ目の機械的な弱さが原因**である
可能性が高い。重ならないことが構造的に保証されれば、AI は密度の高い図にも安心して
挑める。これは磨き上げではなく、いまできないことをできるようにする話である。

2つ目と、3つ目のうちの構成の判断は、レイアウトエンジンだけでは良くならない。
別の仕掛けが要る(2章・3章)。

**いま**:入れ子の Box のレイアウトエンジン(Go、依存ゼロ)で、要素は重ならない作り。
本文が収まらないときは `layout-overflow` の警告で、どのブロックが何 pt はみ出したかを
出す(自動で縮めたり送ったりはしない)。「AI が密度の高い図に挑むようになる」は
**まだ仮説**で、比べる評価は Backlog の `density-eval`(#16)。

## 2. 3つの答え

### 2.1 見た目 → 意味のトークン

配色・余白・字の大きさを自由に選ばせず、検証済みの限られた選択肢からしか選べない
ようにする。スイスのタイポグラフィ(グリッドシステム)の考え方で、個々の判断の
センスに頼らずに、構造的に破綻しない見た目を作る。

- 余白・間隔:決まった刻み(4pt など)だけ。
- 色:16進ではなく `accent`・`text_muted` のような役割名。実際の色は検証済みの
  パレット(テーマ)で一元に持つ。
- 字の大きさ:題・見出し・本文・注のような決まった段だけ。段が決まっていると、
  レイアウトエンジンの文字の計測も安定する。

トークンが届くのは「破綻しない、きちんとした」水準の底上げで、「美しい・記憶に残る」
上限は保証しない。上振れ(構図の妙)には3章の仕掛けが要る。

**いま**:メモより一段強い形で満たしている。**作者(AI)は色も大きさも余白も一切
選ばない**。IR は意味だけを持ち(知らないキーは断る)、見た目はテンプレートの値の表
(`boxloom/templates/<名前>.json`)にある。色は役割名だけ。字体もテンプレートが選び、
字体ごとの実測の寸法で測る(`docs/fonts.md`)。足りないのは、**テンプレートの側の値**
を刻みと段に載せて強制すること(Backlog `value-scales` #29)。

### 2.2 密度 → レイアウトエンジンで測る

密度の判断を AI の主観に任せると精度が低い。レイアウトエンジンを「描く前に測る道具」
として使い、「このブロックにこの量を入れると、確保できる面積を超える」を機械で
判定する。AI に渡す手引き(Skill)は「1ブロックの箇条は N 個まで」のような数値の
目安を持ち、はみ出しそうならスライドを分けさせる。「多すぎるか」を言葉の勘ではなく、
計測の結果で決める。

**いま**:本文の埋まりの検査(`fill-ratio`。65% 未満で警告)と、はみ出しの検査
(`layout-overflow`)がある。どちらも `boxloom check` が誤りと同じ形で返す。
警告が出る前に「あと何 pt・何行入るか」も `check` の `capacity` で数で返す(#9)。
それを使った密度の目安と分け方は Skill(`skills/boxloom/SKILL.md` の4・5章、#10)。
分けるのはエンジンではなく AI の側(エンジンは自動で送らない、と決めてある)。

### 2.3 構成 → 限られた語彙から選ばせる(3章)

## 3. 3層の構想:意味のパターン

コンサルティングの資料が均質で読みやすいのは、自由な発想で描くからではなく、
**内容の型(比較・推移・構成比・因果…)を先に判定し、決まった描き方の
レパートリーに当てはめる**からである(Zelazny『Say It With Charts』、Minto の
ピラミッド原則)。これを仕組みにする。

ソフトウェアの「構造化された中身+逃げ道としての自由記述」(Markdown の中に
部品を埋め込める MDX、Notion の Embed・Canvas のブロック)と同じ発想で、3層に分ける。

1. **スライドのパターン**(一番外):比較・プロセス・統計強調・引用・画像の並び …
2. **キャンバス**:1層目のパターンに収まらない図を描くための枠。
3. **キャンバスの中の図のパターン**:キャンバスの中も完全に自由にはせず、もう1段の
   限られた語彙(プロセス・組織図・マトリクス・ファネル …)を持つ。本当に既存の
   パターンで表せないときだけ、生の図形・矢印・コネクタまで降りる。

「限られた語彙から選ぶほうが、自由に描くより美しくなりやすい」という原則は、
キャンバスの中でも1層目と同じくらい効くはずなので、層を1つ増やす価値がある。

押さえる点が2つある。

- **パターンに当てはめるか、キャンバスに逃げるかを、AI の気分ではなく明文の規則で
  決める。** 曖昧だと、簡単な内容までキャンバスで自由に描いて一貫性が崩れるか、
  図が要る内容をパターンに押し込んで不自然になる。両方向の失敗が起きる。
  → 規則は `docs/patterns.md` の4章(R1〜R14)。
- **キャンバスの内と外の座標の橋渡し。** キャンバスの大きさは外側の並べ方で決まるが、
  中の図は自分の大きさ・縦横比を持つ。当初は拡大縮小して収める(CSS の
  `object-fit: contain`)案だった。**Boxloom は別のやり方を採った**:図が自然・最小・
  上限の大きさを自己申告し、外側のエンジンがそれを見て枠を決め、図は渡された枠に
  合わせて**組み直す**。拡大縮小しないので、図の中の字がテンプレートの段から外れず、
  編集できる PPTX として素直である(`docs/subsystem.md`)。縦横比を持つ図向けの申告は
  Backlog `subsystem-fit`(#23)。

**いま**:
- 1層目:表紙と本文のスライド、ブロックは段落・箇条・比較・注記。語彙の全体と
  優先順は `docs/patterns.md` の3章。表と画像は1層目のブロックにすると決めた。
- 2層目:サブシステムの差し込み口(大きさの自己申告、役割名、テンプレートによる
  差し替え、Schema の名乗り)がある。
- 3層目:Gantt と、生の図形への逃げ道 `shapes`(キャンバスの中だけ、座標は 0〜1、
  色は役割名、重なりは警告)。箱と線の図 `process`・`orgchart`・`matrix`・`funnel`
  (意味だけを書き、置き場所と色はサブシステムが決める。`docs/subsystem.md` の11節)。

## 4. 立ち位置

### 4.1 すでにある半分と、ほぼ無い半分

公開情報で調べた範囲では、「半分は確実にあり、半分はほぼ無い」。

- **ある半分:意味のパターン+自動のレイアウト。** Beautiful.ai(比較・タイムライン・
  統計・引用・画像の並びなど数百の Smart Slide)、Gamma、Tome、Canva の Magic Design、
  Presentations.ai、Plus AI など。「AI が内容から整ったレイアウトを作る」製品は、
  競争の激しいジャンルとして確立している。
- **ほぼ無い半分:それを本物の、編集できるネイティブの PPTX として出すこと。**
  上の製品はほぼすべて Web(HTML/CSS)で作られていて、PPTX は後付けの書き出し先で
  ある。Gamma は技術解説で自社のレンダラーを「Web ネイティブで、スライドの
  オブジェクトのネイティブではない」と書き、複雑なレイアウトは書き出しで画像になり
  編集できない。Beautiful.ai の公式ブログには「PowerPoint への書き出し方、そして
  なぜすべきでないか」という題の記事がある。
- 理由は技術の難しさだけでなく、**自社の Web エディタへの囲い込み**にある。完璧な
  PPTX を書き出せると、利用者は自社の道具から離れやすくなる。気づかれていない
  隙間ではなく、気づいていて投資していない領域である可能性が高い。
- Microsoft(Copilot・PowerPoint Designer)はこの変換の問題を持たないはずだが、
  レイアウトやプレースホルダーの扱いが期待どおりに動かないという声もあり、
  完璧とは言えないようである(詳細は未確認)。

公開情報だけの調査で、社内の非公開の道具までは分からない。

### 4.2 Boxloom が狙う場所

**AI エージェントや開発者が呼び、意味の入力から、編集できるネイティブの PPTX を
作る、セルフホストできる生成エンジン。** Web エディタ(人が触る、きれいな画面)では
競わない。

- 出発点(LaTeX のように宣言的に書く)と合う。
- **SaaS にデータを送れない企業**や、自前の AI エージェントを作る開発者にとって、
  自分の環境で動かせる基盤としての需要がある。Gamma や Beautiful.ai が持たない
  立ち位置である。

**いま**:入口は `boxloom parse`(Markdown → IR)・`check`・`build`・`schema`
(AI に渡す語彙と Schema)・`fonts`。AI に渡す手引きは `skills/boxloom/SKILL.md`(#10)、
Go のライブラリとしての入口は `docs/library.md`(#11)。足りないのは MCP サーバ(#12)。

## 5. OSS にする理由と範囲

- **作る価値:ある。** 資金のある企業が「気づいているが、構造的にやる理由が無い」
  空白で、囲い込む動機を持たない作り手だからこそ埋められる。だから OSS に向いている。
- **範囲は絞る。** 消費者向けのプレゼン作成アプリとして Gamma・Beautiful.ai と同じ
  土俵に立つと、画面の使い勝手への継続的な投資が要り、ボランティアの開発と相性が
  悪い。**インフラ・ライブラリ**として作る。レイアウトエンジン+図形のプリミティブ+
  パターンの語彙が、そのまま無理のない最初の土台になる。

**いま**:リポジトリは公開していない。README(英語)・CONTRIBUTING(審美の決め手を含む)は
ある(#33)。LICENSE は Apache-2.0(人が決めた)。公開の時期は人が決める。

## 6. リスク

1. **描画の忠実性。** OOXML は PowerPoint・LibreOffice・Google Slides・Keynote の
   間で解釈が少しずつ違う。「自分の環境ではきれいだが、別の環境では崩れる」類の
   不具合は、python-pptx や PptxGenJS の課題の一覧にも大量にある。作って終わりでは
   なく、保守の費用が続く。
   - 打つ手:字体をテンプレートで選び、置き換わり得る字体のうち一番広い幅で測る
     (済み、`docs/fonts.md`)。4つのアプリで開いて比べる表(#14)、OOXML の
     機械の検査(#15)。
2. **パターンの選定はデザインの仕事で、エンジニアリングではない。** OSS はコードの
   貢献は集まりやすいが、一貫した審美眼が要る部分は分散した貢献と相性が悪い。
   Tailwind や shadcn/ui のように、少人数の**審美の持ち主**(taste owner)が
   引っ張り続ける必要がある。
   - 打つ手:貢献の方針に「コードは広く受け、パターンとテンプレートの見た目は少人数が
     決める」と書く(#33)。語彙の追加は `docs/patterns.md` の手順で行う。
3. **成功すると、資金のある企業に参考にされ取り込まれる。** それ自体は OSS の成功の
   しるしで悪くない。本当の守りは機能の競争に勝つことではなく、「セルフホストできる」
   「AI エージェントから直接呼べる」という**立ち位置そのもの**だと割り切る。
