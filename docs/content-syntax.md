# コンテンツの記法 — 仕様 第一版(v0.1)

Boxloom の作者が書くコンテンツの記法を定める。候補の比較と理由は
`docs/content-syntax-comparison.md` にある。この文書はその「決定」を受けた仕様である。

> 状態: 第一版。Go 版にパーサーがある(`boxloom/markdown.go`。8章)。要素の名前と
> 範囲は、意味の中間表現(IR)の Schema 第一版(`schema/`・`docs/ir.md`)に揃えてある。
> 食い違ったら IR を正とする。IR にまだ無いものは「予定」と書き、入るまでは誤りとして断る。

## 1. 決定

| 入口 | 位置づけ | 誰が使うか |
|---|---|---|
| **Boxloom Markdown**(`.bx.md`) | **主な入口**。作者が書くのはこれ | 人、AI |
| **IR の写し(YAML / JSON)**(`.yaml`・`.yml`・`.json`) | 併存する入口。IR と1対1(同じキー・同じ `type`) | 他のプログラム、構造化出力で書く AI、構造の多い資料(compare・stat・Gantt など)を書く人 |
| Go DSL | 作者向けにはしない。テンプレート・プラグイン・試験用 | 開発者 |
| TeX 風 | **採らない** | — |

`boxloom parse`・`check`・`build` とライブラリの `ReadDeck` は、拡張子で入口を見分ける
(`.md` は Markdown、`.yaml`・`.yml` は YAML の deck、それ以外は JSON の IR)。既定は当面
Markdown。

**YAML の deck**(IR の写し。例は `examples/yaml/charts.yaml` = `examples/ir/charts.json`):

- キーと `type` は JSON の IR とまったく同じ(写し方を独自にしない)。読んだ結果は JSON の IR に
  して、Go の読み込み(知らないキー・型の違い)と `boxloom check` にそのまま通す。
  `boxloom parse deck.yaml` で JSON の IR が出る。
- 読むのは 3.5 と同じ YAML の部分集合(参照 `&` `*`・タグ `!`・複数文書 `---`・ブロックの
  文字列 `|` `>`・複数行にまたがる値は誤り。改行は `"…\n…"` で書く)。依存は増やさない。
- 値は JSON の形だけで読む:引用(`"…"`・`'…'`)はいつも文字列、引用なしの `true`・`false` は
  真偽値、`null` と空の値は null、引用なしで JSON の数の形(`-1`・`0.5`・`1e3`)なら数、ほかは
  文字列。日付(`2026-04`)は日付型にせず文字列のまま、`yes`・`on` も文字列。題に `2024` のような
  数だけを書くときは `"2024"` と引用する(引用しないと型の誤り。hint で知らせる)。
- 文の中の記法(強調など)は JSON の IR と同じ(インラインの配列 `[{strong: …}]` で書く。
  Markdown の `**…**` は読まない)。
- 誤りは 5章の形で、YAML の `line`・`column` を付ける。YAML の部分集合の外は code `yaml`、
  Go の読み込みが断るもの(知らないキー・型の違い)は `schema`、意味の誤り・警告は
  `boxloom check` の code のまま。場所は IR の場所(`path`)から引いた YAML のキー(列の項目
  なら `-` の後ろ)の位置。

決め手は次の3つ。

1. **作者体験**: スライドの大半は文章と箇条で、Markdown が最も楽に書け、そのまま
   読める。Gantt のような構造の多いデータだけを YAML の囲みに逃がせる。
2. **AI との相性**: AI が最も自然に書ける記法で、トークンも最も少ない。TeX 風は
   AI が本物の LaTeX の見た目の命令(`\vspace` `\textcolor` など)を持ち込むので採らない。
3. **分離を機械で守れること**: Markdown の弱点(約束事を忘れる・誤りが黙って通る)は、
   次の「厳格な Markdown」の規則と `boxloom check` で塞ぐ。

「TeX 的」は記法の見た目ではなく、**意味だけ書けば組版が済む** という思想のほうで実現する。

## 2. 厳格な Markdown — 弱点の塞ぎ方

ふつうの Markdown は「何を書いても何かとして通る」。Boxloom Markdown はその逆で、
**意味が決まらない書き方は誤りとして断る**。

| 弱点 | 塞ぎ方 |
|---|---|
| 見た目で区別する約束事を忘れる(`+`/`-` で良い点・悪い点) | **約束事は名前で書く**。`:::pros` `:::cons` のように囲みの名前で意味を示す。記号の違いに意味を持たせない |
| 知らない囲み・属性が黙って無視される | 囲みの名前・属性・サブシステムのキーは **閉じた一覧**。知らないものは誤り |
| 生の HTML・style で見た目が漏れ込む | 生の HTML は誤り(`<br>` `<span style=…>` を含む) |
| 別の方言が混ざる(`> [!NOTE]`、脚注、表の配置指定 `:--:` など) | 対応しない構文は無視せず誤りにして、代わりの書き方を示す |
| 色・大きさ・位置の指定 | 属性に `color` `size` `align` `x` などは無い。見た目を変えたいときはテンプレートの **変種**(`variant`)を名前で選ぶだけ |
| 囲みの `:::` の入れ子がずれる | 閉じ忘れ・数の不一致は、開いた行の位置つきで誤り |
| 誤りの場所が分からない | すべての誤りを「ファイル・行・列・IR の中の場所・期待したもの・直し方の候補」で返す |

## 3. 文書の形

```
---                      ← 文書の頭(YAML)。省略可
title: …
---
# スライドの題            ← レベル1の見出しが1枚の始まり
本文…
```

### 3.1 文書の頭(front matter)

YAML で書く。使えるキー:

| キー | 意味 | 必須 |
|---|---|---|
| `title` | 文書の題(表紙に使う) | ○(文書の頭を書くなら) |
| `subtitle` | 副題 | |
| `author` | 作者 | |
| `date` | 日付(`YYYY-MM-DD` か `YYYY-MM` の文字列として扱う)。表紙に出す(見せ方はテンプレート) | |
| `confidential` | 機密区分の短い文(例 `社外秘`)。表紙とフッターに出す | |
| `disclaimer` | 文書全体の免責・但し書き。表紙に1回だけ出す | |
| `template` | テンプレートの名前 | |
| `cover` | 表紙を出すか(既定 `true`) | |
| `toc` | 表紙の直後に目次を置くか(既定 `false`)。level 1・2 の区切りを頁番号つきで並べる | |
| `coverImage` | 表紙の写真(PNG / JPEG。文書からの相対パス)。飾りなので代わりの文は要らない | |
| `closing` | 最後に終わりのスライドを置くか(既定 `false`)。1行の文を書けば終わりのスライドを置き、その文を載せる | |

表紙は文書の頭から作る。表紙のためにスライドを書く必要はない。
IR では、文書の頭は `meta` になり、`cover` が `true` なら先頭に `{type: "cover"}` の
スライドが置かれる。`template` は IR の根の `template` になる。文書の頭を書かなければ
`meta` も表紙も無い。`title`・`subtitle`・`author`・`confidential`・`disclaimer` の値は
本文と同じ文中の記法(`**…**` など)で読む。

`toc: true` なら、組み立てで表紙の直後(表紙が無ければ先頭)に目次のスライドを1枚足す
(IR は `meta.toc`。目次のスライドは IR に書かない)。目次には区切りのうち level 1(章)と
2(節)を、目次を足したあとの頁番号つきで並べる。見た目はテンプレートの骨組みの `toc`。
フッターの頁番号も目次を数える。`boxloom check` の誤り・警告の場所(`/slides/N`)は IR の
スライドの番号のまま。

`coverImage` は表紙に敷く写真(IR は `meta.coverImage`)。決まりは画像の `src` と同じで、
文書のファイルからの相対パス・区切りは `/`・PNG か JPEG。絶対パス・URL・文書のフォルダの外
(`..`)は `image-path`、無いものは `image-missing`、PNG・JPEG でないものは `image-format` の誤り
(場所は `/meta/coverImage`)。飾りの写真なので `alt` は書かない。写真は全面に敷き、縦横比が
ページと違えば長い方の両端を切る(引き伸ばさない)。どう重ねるかはテンプレートの骨組み
(標準の表紙は写真の上に今の見た目を重ね、report は写真の上に基調色の箱を置いて白い字で
題・副題・作者・日付をすべて箱の中に書く)。

`closing: true` か1行の文(例 `closing: ご清聴ありがとうございました`)なら、組み立てで最後に
終わりのスライドを1枚足す(IR は `meta.closing`。真偽か文。終わりのスライドは IR に書かない)。
文は本文と同じ文中の記法で読む。`yes`・`no`・`on`・`off` は真偽の書き違いと見なして
`invalid-value`(その語を文にしたいときは `"yes"` と引用符で囲む)。標準は地の色だけで、
`coverImage` があればその写真を全面に敷き、文があれば左下に置く(report は同じ写真に
基調色の箱を置き、文は箱の中に白い字で書く)。終わりのスライドの警告の場所は `/meta/closing`。

```markdown
---
title: 架空の街の移動の調べ
template: report
coverImage: images/cover.jpg
closing: true
---
```

「数字はすべて架空」「社外秘」のような文書全体に掛かる断りは、スライドごとの
`:::note` に繰り返さず、`disclaimer`・`confidential` に1回だけ書く。

### 3.2 スライド

- `# 題` が1枚の始まり。次の `#` か文書の終わりまでがそのスライド。
- `#` の行の末尾に属性を `{…}` で付けられる: `# 論点 {variant=dense}`。
  使える属性は `type`(スライドの種類)と `variant`(テンプレートが名乗る名前)と、
  区切りだけの `level`・本文のスライドだけの `marker` と `density`(下)。
  スライドの `id` は予定(IR 第一版に無い)。
- **スライドの種類は `type` で選ぶ**(省けば `content`)。`#` の行の文の意味は種類で決まる:

  | `type` | `#` の行の文 | 後ろに書けるもの | IR |
  |---|---|---|---|
  | `content`(既定) | 題(短い見出し。1行) | 本文・`:::lead`・`:::notes`・`:::source` | `{type: "content", title, lead?, marker?, density?, body}` |
  | `section` | 章・節・項目の題 | `:::notes` だけ | `{type: "section", title, level?}` |
  | `statement` | 言いたいことの1文 | `:::notes`・`:::source` だけ | `{type: "statement", content}` |

  ```
  # 第2部 移行の進め方 {type=section}

  # 移行は 2 年早める必要がある {type=statement}

  :::notes
  根拠は第1部の数字。ここでは1文だけを言い切る。
  :::
  ```

  - `section`・`statement` の後ろに本文(段落・箇条・囲み・コードブロック)を書くと
    `misplaced-content`。区切りに目次を足す・主張に理由の箇条を足すのは、
    `docs/patterns.md` の R1・R2 の悪い例なので、記法で止める。
  - **区切りの階層**は `level`(1 章・2 節・3 節の中の項目。既定 1):
    `# 返却の流れ {type=section level=2}`。親の無い階層(1 より前の 2、章を変えた後の 3 など)は
    `boxloom check` の `section-level`。1〜3 のほかは `invalid-value`、区切りでないスライドに
    書けば `misplaced-content`。見た目はテンプレートが決める(標準の区切りは階層によらず同じ。
    report は 1・2 を全面の基調色の枠、3 を親の節の題と兄弟の項目の一覧にする)。
  - **隅の印**は `marker`(本文のスライドだけ。空白を含まない2字までの短い文):
    `# 返却箱の使われ方 {marker=A}`。詳細のページで、いまどのパターン・どの要因の話かを示す
    (1・2・A・B)。IR はスライドの欄 `marker`。3字以上・空は `invalid-value`(場所
    `/slides/N/marker`)、本文のスライドでないところに書けば `misplaced-content`。
    今の項目の名前(パンくず)は書かない。テンプレートが、そのスライドより前で最も近い区切り
    (いま開いているいちばん深い level の区切り)の題から作る。見た目はテンプレートが決める:
    report は右上の隅に三角の地(48pt・濃い基調色 `support`)と丸の中の印、その左に
    パンくず(10pt・`text_muted`)を描く(ページの上の余白の中なので、題・本文の配置は
    変わらない)。dark・light は描かない(区切りの `level` と同じく、意味は IR に残り、
    描かないことは check の誤りにも警告にもしない。テンプレートを report に替えれば出る)。
  - **本文の密度**は `density`(本文のスライドだけ。`normal` か `dense`、省けば normal):
    `# 移す仕組みの一覧 {density=dense}`。意味は「このページは参照用に詰めて読ませる」(表・
    一覧の密なページ)。テンプレートが名乗る見た目の名前 `variant` とは別の欄で、どの
    テンプレートでも書ける。dense のスライドは、本文の部品・サブシステムの字の大きさと間隔を
    テンプレートの値の表の `dense` の組(本文・入れ子の箇条・表・小さい字、ブロック・項目の
    間)にする。題・リード・出典・フッターは変えない。IR はスライドの欄 `density`。
    知らない値は `invalid-value`(場所 `/slides/N/density`、`expected` に normal・dense)、
    本文のスライドでないところに書けば `misplaced-content`。Boxloom は自分では dense に
    しない(はみ出しを自動で直さない)。はみ出した normal のスライドには、`layout-overflow` の
    hint が dense で組み直して測った結果(「{density=dense} で収まります」か「dense にしても
    N pt 足りません」)を言う(`docs/ir.md` の 9.4)。
  - `type=cover` は誤り(表紙は文書の頭から作る。3.1)。知らない種類は `invalid-value`
    で、選べる名前を `expected` に入れる。
  - 理由:種類を `#` の行の属性にしたのは、どの種類も「1枚の始まり」と「1つの文」を
    持ち、違うのはその文の意味だけだから。`:::section` のような囲みにすると、スライドの
    境目(`#`)と中身の境目が2重になる。`# ---` のような記号の約束事は使わない
    (2章「約束事は名前で書く」)。
- 1枚目の `#` より前に本文を書くのは誤り(どのスライドのものか決まらない)。
- `---`(水平線)はスライドの区切りではない。誤りにして `#` を使うよう示す。

### 3.3 本文で使えるもの

| 書き方 | 意味 | IR |
|---|---|---|
| 段落 | 文 | `paragraph` |
| `- ` / `1. ` | 箇条(入れ子は3段まで。4段目は誤り)。`1. ` は番号つきの箇条 | `points`(入れ子は `{content, items}`。`1. ` なら `ordered: true`) |
| `**…**` | 強調。**太字ではなく「強調」という意味**。どう見せるかはテンプレート | インラインの `em` |
| `` `…` `` | コード・識別子 | インラインの `code` |
| `[文](URL)` | リンク | インラインの `link` |
| 行末の `\` | 意味のある改行 | インラインの `br` |
| 表(GFM の表) | 行×列の文字・数(3.7) | `table` |
| `![代わりの文](path)` だけの段落 | 画像1枚。2〜6枚を並べると画像の並び(3.8) | `image` / `gallery` |

`1. `(`1) ` も同じ)で始めた箇条は番号つきの箇条(IR の `ordered: true`)。手順・読む
順のように順序に意味があるときに使う。番号は PowerPoint が振り、番号の形(1. ・i. ・①)は
テンプレートが決める(`orderedStyle`)ので、書く数は意味を持たない。ただし始まりは `1.` に
限る(2 以上で始めると `invalid-value`)。2つ目からは `1.` を重ねても `2.` と数えてもよい。
入れ子の箇条も `1. ` で書けば、その入れ子だけが番号つきになる(入れ子の段の形は 1.)。
入れ子は字下げで3段まで書ける(2段目・3段目の印と字の大きさはテンプレートの
`marks.subPoint`・`subPoint`。PPTX では段落の `lvl` 1・2)。4段目は `misplaced`。
同じ段に `- ` と番号を混ぜるのと、`:::pros`・`:::cons` の中の番号は `invalid-value`。

段落の中の改行(行末に `\` の無いもの)は、ふつうの Markdown と同じく改行にならず
次の行とつながる。つなぐとき、**つなぎ目の両側が英数字のときだけ空白を1つ入れ**、
どちらかが日本語なら空白を入れない(ふつうの Markdown は常に空白を入れるので、
日本語の文の途中に空白が入ってしまう)。

`\` の後ろの記号はただの文字になる(`\*` は `*`)。`_` と `&` には意味を持たせない
(ただの文字)。

`*…*`(斜体)・`~~…~~`(取り消し線)・脚注・生の HTML は使えない。強調は1種類に絞る。
意味の違う強調が要るなら、テンプレートが名乗る囲みを増やす(3.4)。

### 3.4 意味ブロック(囲み)

`:::名前` で開き `:::` で閉じる。中に別の囲みを入れるときは、**外側の囲みのコロンを
1つ増やす**(`::::compare` の中に `:::option`)。閉じも同じ数のコロンで書く。
名前の後ろに見出しの文、その後に属性を書ける:

```
:::名前 見出しの文 {属性=値}
中身(Markdown)
:::
```

第一版の囲み(既定のテンプレートが名乗るもの):

| 囲み | 中に書けるもの | 意味 | IR |
|---|---|---|---|
| `compare` | `option` だけ(2つ以上) | 選択肢の比較 | `compare` |
| `option 名前` | `pros`・`cons` だけ | 比較の1つの選択肢 | `compare.options[]`(`label` が名前) |
| `pros` / `cons` | 箇条 | 良い点 / 悪い点 | `pros` / `cons` |
| `note` | 本文 | 注記・但し書き | `note` |
| `takeaway` | 段落1つ | 本文の中で言いたいことを1文で目立たせる(結論) | `takeaway` |
| `stat` | `value` だけ(1〜4個) | 数を強く見せる(統計強調) | `stat` |
| `value 数` | 段落1つ(数の説明) | `stat` の1つの数。見出しの文が数、属性 `unit` が単位 | `stat.items[]`(`value`・`unit`・`label`) |
| `quote 出どころ` | 段落1つ(引用した言葉) | 他人の言葉。見出しの文が出どころ(必須) | `quote`(`content`・`source`) |
| `notes` | 段落・箇条 | 発表者ノート(スライドには出ない)。3.6 | スライドの `notes` |
| `columns` | `column` だけ(2つか3つ) | 並列のまとまり(段組みの指定ではなく「並列」という意味)。属性 `flow=true`(左が右につながる)。3.9 | `columns`(`flow`) |
| `column 題` | 段落・箇条・表・画像・画像の並び・`note`・`pairs`・`people`(1〜2人)・`topics`・```` ```chart ````・```` ```cycle ````・```` ```phases ````・```` ```matrix ````・```` ```orgchart ````・```` ```pillars ```` | 並列のまとまりの1つ。題は省ける。属性 `role=main` | `columns.columns[]`(`title`・`role`・`body`) |
| `pairs 見出し \| 見出し` | `subject`・`response` を交互に(2組以上) | 対の並び(標準でない型)。2つの側の見出しを1回だけ書く。3.10 | `pairs`(`headings`・`pairs`) |
| `people` | `person` を1〜4個(まとまりの中は1〜2個) | 人物の紹介(標準でない型)。3.11 | `people`(`people`) |
| `person 名前 {role=… image=… alt=…}` | 経歴の段落か箇条を1つ(無くてもよい) | 1人の紹介。名前は必須、写真には `alt` も | `people.people[]` |
| `subject 見出し` / `response 見出し` | 段落・箇条・`quote` のどれか1つ、または見出しの文と段落・箇条・`quote`・画像・表の1〜4個 | 対の何についての側 / それに応える側(見出しの文は任意) | `pairs.pairs[].subject` / `.response`(1つのブロックか `{title, body}`) |
| `topics` | `topic` を2〜6個 | 印つきの塊の並び(標準でない型)。3.11 | `topics` |
| `topic 題` | 段落・箇条・`quote` の1〜3個。属性 `label`(2字まで。全てに付けるか全てに付けない) | 塊の1つ。3.11 | `topics.topics[]`(`title`・`label`・`body`) |

```
:::takeaway
減った問い合わせの大半は **初回の登録** に関するものだった
:::

::::stat
:::value 3 → 12 {unit=機種}
対応する端末の機種
:::
:::value −40 {unit=%}
月あたりの問い合わせ(前年同月比)
:::
::::

:::quote 窓口担当 A、2026 年 9 月の聞き取り
前は登録のたびに 3 つの画面を行き来していたが、いまは 1 つの画面で終わる。
:::
```

- `takeaway`・`quote`・`value` の中は段落1つ(改行したいなら行末に `\`)。空・2つ目の
  段落・箇条は `misplaced-content`。`takeaway`・`stat` は見出しの文を持てない。
- `value` の見出しの文は **書いたとおりの文字** で IR の `value` になる(文中の記法は読まない)。
  数字を1つも含まないものは `invalid-value`、無いものは `missing-key`。属性は `unit` だけで、
  値は空白を含まない1語(`{unit=%}`・`{unit=機種}`)。`value` が5つ以上は `misplaced-content`
  (系列は表・グラフ。`docs/patterns.md` の R3・R4)。`value` を `stat` の外に書くのも誤り。
- `quote` の見出しの文が無ければ `missing-key`(他人の言葉は出どころと対。R11)。
- 理由:
  - 引用を `>` で書かないのは、`>` が GFM の注意書き(`> [!NOTE]`)・メールの引用など
    複数の意味で使われ、出どころを書く場所も無いため(`>` は引き続き `unsupported-syntax`
    で、`:::quote` を示す)。出どころを「— 名前」の行のような記号の約束事にもしない。
  - 出どころを囲みの見出しの文にしたのは、`:::option 名前` と同じく「囲みの名前の後ろ =
    その囲みが名乗る意味の短い文」の形に揃えるため(何の文かは `boxloom schema` の
    `label` が名乗る)。
  - 数を箇条(`- 12 台 対応機種`)で書かないのは、どこまでが数・単位・説明かを空白の位置で
    決めることになり、意味が記号と位置に頼るため。`:::value` の見出し・属性・中身の3か所に
    名前つきで分けた。

いまは「予定」の囲みは無い。

囲みの一覧はコアが固定で持つのではなく、**型の語彙とサブシステムが名乗る**
(`docs/layers.md` の8.2。型の囲みはテンプレートに依らず同じで、`boxloom schema` の
`blocks` に出る)。名乗っていない囲みを使うと誤りになる。囲みの名乗り(`BlockDecl`)は
置き場所と中に書けるものを宣言するだけで、中身から IR の欄への写し方は型ごとのコードが
持つ(`docs/layers.md` の8.3)。

入れ子は3段まで(`columns` と `column` は数えない。まとまりの中は本文と同じだけ入れ子にできる)。閉じの省略は許さない(AI も人も、省略規則は忘れやすいため)。

### 3.5 サブシステム

言語名つきのコードブロックで、中身は YAML。言語名がサブシステムの名前:

````
```gantt
span: 2026-09 .. 2034-11
groups: …
```
````

- 中身はサブシステムが名乗る Schema で検査する。知らないキーは誤り。
- 中身は IR の Gantt の `data`(`schema/subsystems/gantt.schema.json`)と同じキー。
- 状態は意味役割名(`support` `conditional` `none` `danger`)。色は書けない。
  ハードウェアのリスクのような「期間の性質」は状態ではなく、グループの `risk: A .. B`。
- 注釈は位置や上下を持たない。どのグループ・行に付くかを `target`(`id`)で示し、
  置き場所はサブシステムが決める。
- 日付は `YYYY-MM` か `YYYY-MM-DD`。YAML の日付型への自動変換はせず、文字列として
  受け取ってサブシステムが解釈する。範囲は `A .. B` と書け、パーサーが IR の
  `{from, to}` に変える。複数行のラベルは YAML の配列で書く(IR の行の配列になる)。
- YAML は落とし穴の少ない部分集合で読む: 参照(`&` `*`)・タグ(`!`)・複数文書は誤り。
  真偽値は `true` / `false` だけ(`yes` `no` `on` `off` は文字列)。
- 文の値(IR でインラインのもの:`label`・`text`・凡例の説明など)は、本文と同じ
  文中の記法で読む(`**…**`・`` `…` ``・`[文](URL)`)。**YAML の列で書くと、各行を
  意味のある改行(`br`)でつなぐ**:`text: [ここまでに全利用者を, Board B/C へ移行予定]`。
  グループの `label`(IR で行の配列のもの)は、列がそのまま行の配列になる。
- 範囲は `A .. B` のほか、IR と同じ `{from: A, to: B}` でも書ける。
- 流れの書き方(`{…}` `[…]`)は1行の中で閉じる。複数行にまたがる値・ブロックの
  文字列(`|` `>`)は誤り。値の中に「: 」を書くときは `"…"` で囲む。
- コードブロックの言語名の後ろに `{variant=名前}` を書ける(IR のサブシステムの
  `variant`)。
- **```shapes**(生の図形への逃げ道。既存のパターンで表せない図のときだけ使う最後の手段。
  `docs/subsystem.md` の8節)も同じ作り。中身は IR の shapes の `data` と同じキー。
  座標と大きさは引用しない数(0〜1)、線の点は流れの書き方の列(`from: [0.1, 0.5]`)、
  色は役割名、文字の大きさは `textStyle` の段の名前で書く。

  ````
  ```shapes
  aspect: 2.6
  items:
    - {id: web, kind: roundRect, x: 0.22, y: 0.38, w: 0.15, h: 0.24, text: Web 層, line: accent}
    - {id: api, kind: rect, x: 0.44, y: 0.38, w: 0.15, h: 0.24, text: API 層, fill: accent, textColor: on_conditional}
    - {kind: connector, from: web, to: api, arrow: true}
  ```
  ````

  パーサーが断るのは形の誤り(知らないキー・0〜1 の外・引用した数・16進の色・知らない
  段)だけ。`x+w` が 1 を超える・テーマに無い役割名・無い id へのコネクタは
  `boxloom check` が、図形やキーの行と code(`shape-bounds`・`role-exists`・
  `target-exists`)で返す。例は `examples/md/shapes.bx.md`(↔ `examples/ir/shapes.json`)。
- **```process**・**```orgchart**・**```matrix**・**```funnel**・**```phases**・**```cycle**・**```pillars**(箱と線の図・輪の図。
  `docs/subsystem.md` の11節)も同じ作り。中身は IR の `data` と同じキーで、書けるのは
  文と状態(`status`)と強調(`emphasis`)と、状態の意味の凡例(`legend`)だけ(座標・色・
  字の大きさは書けない)。matrix の推す列は `emphasis: <列の見出しの文>`、行の題の下の
  説明は `detail`(1行なら文、YAML の列なら文の列で各行が箇条)、列の見出しの上の群は
  `columnGroups: [{title: 名前, span: 2}]`(span は1以上の引用しない整数。合計は列の数)。funnel の
  `value` は引用しない数なら数、それ以外は文字列。phases の箱の `detail` は1行なら文、
  YAML の列なら文の列(各行が箇条。process と違って改行でつながない)。cycle の段は3〜6つ、
  `start` は 0 か 1(引用しない数)。

  ````
  ```process
  steps:
    - {title: 申請, detail: 申請者が書く}
    - {title: 審査, detail: [平均3営業日, "**ここが詰まる**"], emphasis: true}
    - {title: 承認, status: support}
  ```
  ````

  パーサーが断るのは形の誤り(知らないキー・知らない状態の名前・型)だけ。matrix の
  行のセルの数が列の数と違うこと・`emphasis` が見出しに無いことは `boxloom check` が
  `matrix-cells`・`matrix-emphasis`・`matrix-column-groups`(その行の行つき)で返す。`status` を使ったのに
  `legend` に文が無いと警告 `figure-legend`。例は `examples/md/figures.bx.md`(↔ `examples/ir/figures.json`)。
- **```chart**(数値のグラフ。`docs/subsystem.md` の12節)も同じ作り。書くのは比べ方
  `compare`(item・timeSeries・component・frequency・correlation)と、項目・系列・値・
  単位・強調だけで、グラフの形・色・大きさは書けない(形は比べ方とデータの数から
  サブシステムが選ぶ)。値は引用しない数(`"2"` は誤り)、散布図の点は `[x, y]`。

  ````
  ```chart
  compare: timeSeries
  unit: 件
  categories: [4月, 5月, 6月, 7月, 8月, 9月]
  emphasis: [9月]
  series:
    - name: 申込数
      values: [120, 150, 170, 210, 260, 340]
  ```
  ````

  パーサーが断るのは形の誤り(知らないキー・知らない比べ方・引用した数・点の形)だけ。
  値の数が項目の数と違う・強調する項目が無いなどは、`boxloom check` が `chart-values`・
  `chart-emphasis`(その欄の行つき)で返す。例は `examples/md/charts.bx.md`
  (↔ `examples/ir/charts.json`)。
- サブシステムの名前でないコードブロック(` ```go ` など)と言語名の無い
  コードブロックは、**いまは誤り(予定)**。IR 第一版にコードのブロックが無いため
  (冒頭の「食い違ったら IR を正とする」)。IR にコードのブロックが入ったら、
  ふつうのコードとして扱う。

### 3.6 発表者ノート

スライドの本文の一番外側に `:::notes` を置くと、その中身がスライドの発表者ノート
(IR のスライドの `notes`)になる。スライドの見た目には何も足さない。

```
# 今期の進め方

- 第1段階で試作を作る

:::notes
第1段階の「5 人」は目安。\
増やせるかは次の会議で決める。

話す順:
- 試作の狙い
  - 見た目より流れを確かめる
:::
```

- 置ける場所はスライドの一番外側だけ(`:::compare` などの中は誤り)。本文の前でも
  後ろでもよい。**1枚に1つ**(2つ目は誤り)。
- 最初のスライド(`# 題`)より前に置いた `:::notes` は**表紙のノート**になる。
  表紙が無い(文書の頭が無い・`cover: false`)ときは誤り。
- 中に書けるのは段落と箇条(入れ子は2段まで)だけ。囲み・コードブロック・
  生の HTML は誤り。見出しの文と属性は付けられない。
- ノートは見た目を持たないので、IR では**文字だけの文字列**になる。文中の記法は
  本文と同じく検査したうえで文字にする: `**…**` と `` `…` `` は中の文字、
  `[文](URL)` は `文 (URL)`、行末の `\` は改行。
- 段落と箇条の項目は1つずつ改行で区切る(空行は残らない)。箇条は `- ` を頭に付け、
  入れ子の項目はさらに空白2つで字下げする。上の例の IR の `notes` は
  `"第1段階の「5 人」は目安。\n増やせるかは次の会議で決める。\n話す順:\n- 試作の狙い\n  - 見た目より流れを確かめる"`。
- 例は `examples/md/speaker-notes.bx.md`(IR は `examples/ir/speaker-notes.json`)。

### 3.6.0 リード文

本文のスライドの一番外側に `:::lead` を置くと、その中の段落がスライドのリード文
(IR のスライドの `lead`)になる。このスライドで言いたいこと(結論)を1〜2行の文で書く。
題(`#` の行)は何の話かを短く名指す見出しにし、1行に収める(折り返すと警告 `title-wrap`)。

```
# 問い合わせの回り道

:::lead
問い合わせの 4 割は、最初の窓口では片づかずに別の窓口へ回されている。
:::

- 回された問い合わせは、解決までに平均 2.3 日長くかかる
- 回す先の多くは料金の窓口で、回す理由の半分は権限の不足
```

- 置ける場所はスライドの一番外側だけ(囲みの中は誤り)。題の直後に置く。**1枚に1つ**。
- 本文のスライドだけに書ける。区切り(章の題がそれ)・主張(`#` の行の1文がそれ)・
  最初の `#` より前(表紙)は誤り。
- 中に書けるのは段落1つだけ。見出しの文と属性は付けられない。文中の記法は本文と同じ。
- 見た目と置き場所はテンプレートが決める(dark / light は題の直下に `leadText` の字で)。
  本文の流れの外の枠なので、本文の領域はその分だけ狭くなり、`layout-overflow` と容量の
  測りに入る。行の数の上限はテンプレートが値の表の `leadMaxLines` で持ち(report は2行、
  dark / light は上限なし)、越えると警告 `lead-wrap`。

### 3.6.1 出典

スライドの本文の一番外側に `:::source` を置くと、その中の段落がスライドの出典
(IR のスライドの `source`)になる。数・表・引用・図の出どころ、調査の母数、時点を書く。

```
# 問い合わせの4割は、最初の窓口では片づかずに回されている

::::stat
:::value 41 {unit=%}
最初の窓口から別の窓口へ回された問い合わせの割合
:::
::::

:::source
問い合わせの記録 12,480 件(2026 年 4〜9 月)の集計
:::
```

- 置ける場所はスライドの一番外側だけ(囲みの中は誤り)。本文の前でも後ろでもよい。
  **1枚に1つ**(2つ目は誤り。複数の出どころは1つの段落に書き、改行は行末の `\`)。
- 本文のスライドと主張のスライド(`type=statement`)に書ける。区切りのスライドと、
  最初の `#` より前(表紙)は誤り。
- 中に書けるのは段落1つだけ。見出しの文と属性は付けられない。文中の記法は本文と同じ。
- 見た目と置き場所はテンプレートが決める(dark / light は本文の下・フッターの上に、頭に
  「出典:」を付けた小さな控えめな字)。本文の流れの外の枠なので、本文の領域はその分だけ
  狭くなり、`layout-overflow` と容量の測りに入る。
- 使い分け:出どころ・母数・時点は `:::source`、但し書き(数の読み方の注意など)は
  `:::note`、他人の言葉の出どころは `:::quote` の見出しの文。
- 例は `examples/md/evidence.bx.md`(IR は `examples/ir/evidence.json`)。

### 3.7 表

GFM の表で書く。1行目が見出しの行、2行目が区切りの行、3行目からが本体。

```
| 世代 | 台数 | 保守の期限 |
| --- | --- | --- |
| 第1世代 | 120台 | 2027-03 |
| 第2世代 | 85台 | 2029-12 |
: 台数は2026年10月の棚卸しによる
```

- 行は `|` で始めて `|` で終える(終わりの `|` が無いのは誤り)。
- **列の配置の指定(`:--` `:--:` `--:`)は誤り**(`unsupported-syntax`)。配置は
  テンプレートが決める:dark / light は、本体のセルがすべて数(`120台`・`12.5%`・
  `1,200` のような、数と短い単位)の列を右に揃え、ほかは左に揃える。
- どの行も見出しと同じ数のセル(違えば `table-shape`)。空のセルは `| |`。
- セルの中はインラインだけ(強調・コード・リンク)。`\|` はセルの中の文字の `|`
  (コードの中でも)。囲み・改行は書けない。箇条は下の `{points=列名}` で宣言した列の
  中だけ。
- 表の**すぐ次の行**の `: 説明` は表の説明の文(IR の `caption`。空行を挟むとふつうの段落)。
- **合計の行**:表の最後の行が合計なら、説明の行の末尾に `{total=last}` を書く。最後の行が
  IR の `total`(本体の `rows` とは別の欄)になり、テンプレートが本体の行と見分けて描く
  (dark / light は太字と上の濃い線)。説明の文が無いときは `: {total=last}` だけを書く。

  ```
  | 費目 | 1年目(万円) | 2年目(万円) |
  | --- | --- | --- |
  | 導入 | 1,200 | 0 |
  | 人件費の減り | −1,800 | −1,800 |
  | 差し引き | −600 | −1,800 |
  : 費用は見積もり {total=last}
  ```

  値は `last` だけ(ほかは `invalid-value`)。合計の行のほかに本体の行が1つも無いのは
  誤り。合計の値は計算しない(書いたとおりに出す)。理由:合計の行は意味なので IR では
  `total` という欄に持つ。GFM の表には合計の行の書き方が無いので、記号(区切りの行を
  もう1本引くなど)ではなく、名前のついた属性で書く(2章「約束事は名前で書く」)。
- **行の群**:先頭の列が行の群の名前なら、説明の行の末尾に `{groups=first}` を書く。
  群の名前は群の最初の行の先頭のセルに書き、続く行の先頭のセルは空(`| |`)にする。空の
  セルは上の群の続き。IR では `groups`(群ごとの名前と行の数)になり、本体の行のセルは
  群の列を除いたもの(`docs/ir.md` の設計判断12)。テンプレートが群の名前を縦に結合した
  セルで描く(PPTX の `a:tbl` の `rowSpan`・`vMerge`)。

  ```
  | 群 | 項目 | いま | 見直したあと |
  | --- | --- | --- | --- |
  | 手続き | 見積もりの依頼 | 担当ごとに書式が違う | 書式を1つにする |
  | | 承認の段数 | 金額によらず4段 | 100 万円未満は2段 |
  | 体制 | 窓口 | 部署ごとに7つ | 調達の係に1つ |
  : 見直しの案 {groups=first}
  ```

  - 値は `first`(先頭の列)か、見出しの行の列名(文と完全に一致)。半角の `,` で複数の
    列を群の列にできる(次の「2列目以降の群の列」)。見出しに無い列名・同じ列を2度は誤り
    (`invalid-value`、path は `…/groups`、行は説明の行)。先頭の列の名前は `first` と同じ。
  - 最初の行の先頭のセルが空なのは誤り(`table-groups`、path は `…/groups/0/label`。
    続く群が無い)。
  - 群の列のほかに列が無い表(1列だけ)は誤り(`misplaced-content`)。
  - `{total=last}` と一緒に書ける(`{groups=first total=last}`)。合計の行は群に入らず、
    先頭のセルもそのまま合計の行のセル(「合計」など)。
  - `{groups=first}` の無い表の空のセルは、これまでどおりただの空のセル(上の行の続きには
    ならない)。群の列以外の列の空のセルも、ただの空のセル。
  - 理由:GFM の表にはセルの結合の書き方が無いので、記号(`^` や `〃`)ではなく、名前の
    ついた属性で「先頭の列は群」と宣言する(合計の行と同じ。2章「約束事は名前で書く」)。
    空のセルを続きと読むのは、その宣言のある表の先頭の列だけ。
- **2列目以降の群の列**:同じ値が続くセルを、先頭の列でない列でも縦に結合したいときは、
  `{groups=列名}` でその列を指す(`{groups=区分,支援事業}` のように `,` で複数。`first` と
  並べてもよい)。どの群の列でも、空のセルは上の群の続き。IR では先頭の列は `groups`、
  2列目以降は `groupColumns`(`[{column: 見出しの列の番号, groups: [...]}]`、左から)になり、
  本体の行のセルはどの群の列も除いたもの(`docs/ir.md` の設計判断12)。

  ```
  | 区分 | 支援事業 | 制度 | 上限 |
  | --- | --- | --- | --- |
  | 国 | 創業の支援 | 創業の補助 | 200 万円 |
  | | | 専門家の派遣 | 年 10 回 |
  | | 設備の支援 | 設備の補助 | 1,000 万円 |
  | 県 | 設備の支援 | 設備の貸付 | 3,000 万円 |
  | | | 利子の補給 | 年 1% |
  : 制度の一覧 {groups=区分,支援事業}
  ```

  - 後ろ(右)の群の列は、前(左)の群の列の境を越えて結合しない(入れ子)。左の群の列で
    新しい群が始まる行では、右の群の列のセルにも名前を書く(上の例の県の「設備の支援」)。
    空のままなのは誤り(`table-groups`、path はその列の新しい群の `…/label`)。
  - 群の列の最初の行のセルが空なのは誤り(`table-groups`、path は
    `…/groupColumns/K/groups/0/label`)。
  - 群の列は箇条の列(`{points=列名}`)にできない(`table-points`)。合計の行は群に入らず、
    どの群の列のセルもそのまま合計の行のセル。
  - 描き方:どの群の列も本物の縦の結合(`rowSpan`・`vMerge`)。先頭の列の群の見た目
    (report の縦書きの帯、#100)は先頭の列だけで、2列目以降の群は本体の行と同じ字・面の
    横書きの結合セル。表を分ける案(容量の `split`)は、いちばん左の群の列の境で分ける。
  - 続きの表({continues})は群の列を最初の表から引き継ぐ。続きの表の最初の行には、どの
    群の列にも群の名前を書く。例は `examples/md/table-group-columns.bx.md`。
- **セルの中の箇条**:ある列のセルに2〜4項目の箇条を入れたいときは、説明の行の末尾に
  `{points=列名}` を書く。その列のセルは「半角の `;` で区切った箇条」として読む。IR では
  セルが `{"points": [...]}` になり(`docs/ir.md` の設計判断13)、テンプレートがセルの中の
  箇条の段落として描く(PPTX の `a:tbl` のセルの段落の印 `a:buChar`。印はテンプレートの
  `marks.point`)。

  ```
  | 課題 | いまの手当て | 見直しの案 |
  | --- | --- | --- |
  | 承認が遅い | 催促のメール | 100 万円未満は2段;承認の期限を3日に |
  | 書式がばらばら | 見本を共有 | 書式を1つにする;入力の欄を必須に;古い書式は受け付けない |
  : 見直しの案 {points=見直しの案}
  ```

  - 列名は見出しの行の文と**完全に一致**させる(前後の空白は除く)。複数の列は
    `{points=列名1,列名2}`(列名に空白・`,` を含む列は指せない)。ほかの属性と一緒に
    書ける(`{groups=first points=見直しの案}`)。
  - 文としての `;` を残したいときは `\;` と書く(`;` が区切りになるのは、名前で指した
    列のセルの中だけ。ほかの列の `;` はただの文字)。
  - 項目が1つだけのセル(`;` を含まないセル)は、ただの文字列のセルになる(`親; - 子` は
    親と子の2つの段落なので箇条)。
  - **2段の箇条**:`;` で区切った項目のうち `- ` で始まるものは直前の項目の子(2段目)。
    例 `親の項目; - 子; - 子; 次の親`。IR では子を持つ項目が `{"text": …, "children": [...]}`
    になり、PPTX では子の段落が `lvl="1"` で、印はテンプレートの `marks.subPoint`(親の文の
    頭にそろえて字下げする)。セルの中は2段まで(子の子は書けない)。最初の項目が `- ` で
    始まるのは誤り(`table-points`)。文字の `-` で項目を始めたいときは `\-` と書く。
  - 空の項目(`a;;b`・先頭や末尾の `;`)は誤り(`table-points`、path はセルの項目
    `…/rows/R/C/points/I`)。見出しに無い列名・群の列(`{groups=…}` で指した列)は
    誤り(`table-points`、path は `…/points`、行は説明の行)。
  - 合計の行のセルも同じ列なら箇条として読む。見出しの行のセルは箇条にならない。
  - 理由:GFM の表のセルには箇条の書き方が無い。記号(`;`)に意味を持たせるのは、名前で
    宣言した列の中だけにする(2章「約束事は名前で書く」)。`<br>` のような生の HTML は使わない。
  - はみ出しと容量はセルの中の箇条の行(項目ごとに折り返した行の和。子の項目は字下げの分
    狭い幅で折り返す)を数えて行の高さを決める。
- 列の幅は書かない。テンプレートが中身から測る(折り返さない幅と、見出しの文字列・
  折れない語の幅を守る最小の幅。`docs/fonts.md` の字体の幅。規則は `docs/ir.md` の15章)。行が多くて収まらなければ `layout-overflow`
  の警告で、字を小さくしたり次のスライドへ送ったりはしない。警告の hint と容量の `split` に
  分け方の案(何枚に分けられるか・どの行の前で分けるか)が付く(`docs/ir.md` の「容量の計測」)。
- **長い表を次のスライドへ続ける**:表を作者が分け、続きのスライドの表は**見出しの行を
  書かずに区切りの行から始め**、説明の行に `{continues}`(値を書かない属性)を書く。
  IR では `"continues": true` で `header` が無い表になる(`docs/ir.md` の設計判断14)。

  ```
  # 移す仕組みの一覧

  | 仕組み | 使う部署 | 利用者(人) |
  | --- | --- | --- |
  | 受注の管理 | 営業 | 420 |
  | 見積もりの作成 | 営業 | 380 |
  : 移す仕組みの一覧

  # 移す仕組みの一覧

  | --- | --- | --- |
  | 請求書の発行 | 経理 | 60 |
  | 合計 | | 860 |
  : {continues total=last}
  ```

  - 続きの表は、すぐ前のスライドの最後の表に続く(間に別のスライドを挟まない。外れは
    `table-continues`、行はその表)。
  - 見出しの行・列の数・`{groups=…}`・`{points=列名}` は直前の表から引き継ぐ(書かなくて
    よい)。書くなら同じに(違えば `table-continues`)。区切りの行のセルの数が前の表の列の数と
    違えば `table-continues`。`{total=last}` はひと続きの最後の表だけに書く。
  - `{continues}` の表に見出しの行を書くと誤り(`table-continues`、path は `…/header`)。
    `{continues}` の無い表を区切りの行から始めるのも誤り(`misplaced-content`)。
  - `{groups=…}` の続きの表の最初の行には、群が前の枚から続いていても群の名前を書く。
  - Boxloom が各枚に見出しの行と「n/m」の印(テンプレートの `marks.tableContinued`)を付け、
    列の幅を全部の枚でそろえる。説明の文を書かなければ最初の表の説明の文を繰り返す。
  - 理由:自動で送ると IR の1スライド = PPTX の1枚が崩れ、どこで分けるか(意味の切れ目)は
    作者が決めることなので、分けるのは作者、そろえるのは Boxloom にする。続きの表に見出しの
    行を書かせないのは、同じ見出しを何度も書いて食い違うのを防ぐため。
- PPTX では本物の表(`a:tbl`)になり、PowerPoint・LibreOffice で表として編集できる。

### 3.8 画像

**画像だけの段落**に書く。1枚なら `image`、2〜6枚を空白か改行で並べると `gallery`。

```
![受付の画面の試作。左に窓口の一覧、右に週ごとの件数](images/screen.png "試作の画面")

![第1段階](images/step-1.png "1. 受け付ける") ![第2段階](images/step-2.png "2. 振り分ける")
```

- **代わりの文(`[…]`)は必須**。空なら `image-alt`。画像が何を示すかを1文で書く
  (読み上げと、画像が無いときに使う。PPTX では画像の代わりの文 `descr` になる)。
- `"…"`(Markdown の title)は画像の説明の文(IR の `caption`)。画像の下に出る。
- path は**文書のファイルからの相対パス**(区切りは `/`)。URL・絶対パス・文書の
  フォルダの外(`..`)・`\` は `image-path` の誤り。ファイルが無い・読めないものは
  `image-missing`、PNG・JPEG でないもの(SVG・GIF なども)は `image-format`
  (この2つは `boxloom check`・`build` が見る。パーサーはファイルを読まない)。
- 文の中に画像を書くのは誤り(`misplaced-content`)。7枚以上も誤り。
- 縦横比を保って枠に収める(切り抜かない・引き伸ばさない)。余りは右と下に残る
  (左上に寄せる)。2〜3枚の並びは1段、4枚は 2×2、5〜6枚は3列の2段。
- 画像と文を横に並べたいときは、画像の属性ではなく **`::::columns`** で書く(3.9)。

### 3.9 並列のまとまり

```
:::::columns
::::column 札の並べ方 {role=main}
- 1枚の札に1件の受付
- 丸の色は状態

:::note
色だけで状態を示さない
:::
::::
::::column
![手持ちの端末の画面の試作](images/device.jpg)
::::
:::::
```

- `columns` の中は `column` だけで、2つか3つ。4つ以上の並列で、それぞれ1行なら箇条にする。
- `:::column` の後ろの文はまとまりの題(省ける)。題は意味の一部なので IR の `title` になる
  (`##` の小見出しは使わない)。
- **幅の比は数では書かない。** 主のまとまり(ほかはそれを補う)に `{role=main}` を付ける
  (1つの `columns` に1つまで)。どれだけ広くするかはテンプレートが決める
  (dark / light は値の表の `columnMainWeight` = 2、ほかは 1)。付けなければ同じ幅。
  `width` などの属性は無い(`unknown-attribute`)。
- 中に書けるのは段落・箇条・表・画像・画像の並び(2〜6枚の画像だけの段落)・`:::note`・
  対の並び(`:::pairs`)・グラフ(```` ```chart ````)・循環の図(```` ```cycle ````)・
  フェーズの図(```` ```phases ````)・評価の格子(```` ```matrix ````)・組織図
  (```` ```orgchart ````)。`columns` の入れ子・`compare`・ほかのサブシステム(gantt・
  process・funnel・shapes。本文の幅を前提にする図)は書けない(`misplaced-content`)。
  図の横に読み取り・段ごとの説明・抜き出した一覧を置く(左に図・右に文)のがこの形の
  主な使い道。
- 図は **まとまりの幅で測る**(幅を受けて高さを申告する)。phases・matrix・orgchart・cycle は
  文が箱に入る一番狭い幅を「まとまりの幅の下限」として申告し、まとまりはそこまで広がる
  (ほかの伸びるまとまりから取る)。取りきれなければ図の既存の警告(`subsystem-min`・
  `figure-text-overflow`)。画像の並びは、枡の幅が画像の下限(値の表の `imageMinHeight`)に
  満たなければ列を減らして段を増やす。対の並びは列の中でも同じ組み方(行がそろう)。
  円グラフと輪は高さで大きさが決まるので、まとまりの幅を使い切らないと `spare-width` に
  なる(図のまとまりに `role=main` を付けない・文を足して縦を使う)。
- まとまりの中の図・対の並び・表・画像には、本文に置いたときと同じ誤りが同じ code で出る
  (matrix の `matrix-cells`・`matrix-emphasis`・`matrix-column-groups`、pairs の側の
  `empty-text`・`variant-exists`、表の `table-shape`、画像の `image-missing` など)。場所は
  まとまりの中のブロック(`/slides/S/body/N/columns/C/body/K/…`)を指す(`docs/ir.md` の
  check の表)。
- 中に囲みを持つ `:::pairs` を置くときは、外の囲みのコロンを増やす(外ほど多い):

  ```
  :::::::columns
  ::::::column 抜き出した論点
  - 返却の半分は閉館後に集まる
  ::::::
  ::::::column 論点と打ち手 {role=main}
  :::::pairs 分かったこと | 打ち手
  :::subject
  返却は閉館後に集まる
  :::
  :::response
  返却箱を2つに増やす
  :::
  …
  :::::
  ::::::
  :::::::
  ```

  例は `examples/md/columns-figures.bx.md`(↔ `examples/ir/columns-figures.json`)。
- はみ出しはまとまりごとに測る(一番高いまとまりがブロックの高さを決める)。
  `layout-overflow` は、まとまりの中のはみ出したブロックを
  `/slides/S/body/N/columns/C/body/K` で指す。
- **流れ(`{flow=true}`)**:左のまとまりが右のまとまりにつながる(背景→ゴール、
  発見→対応、前提→結論)ときは、`columns` の囲みに `{flow=true}` を付ける(IR の
  `flow: true`。既定は `false` で、書かなければ並列で対等)。値は `true` か `false` だけ
  (ほかは `invalid-value`)。つながりの印はテンプレートが描く(dark / light はまとまりの間の
  隙間の真ん中に基調色の小さい矢印、report は列の間の縦の罫線の真ん中に丸い矢印)。
  それぞれのまとまりが1行の手順なら `process`(箱を矢印で並べる図)にする。

  ```
  :::::columns {flow=true}
  :::column 分かったこと
  - 返却の半分は閉館後に集まる
  :::
  :::column 打ち手
  - 返却箱を2つに増やす
  :::
  :::::
  ```

### 3.10 対の並び(pairs)

「分かったこと ↔ 打ち手」のように、2つの側の見出しを1回だけ書き、その下に対を並べる。
対の2つの側は行がそろう。標準でない型で、組み方を持たないテンプレートでは `columns`
で組まれる(警告 `component-fallback`。`docs/ir.md` の設計判断10.1)。例は
`examples/md/pairs.bx.md`。

```
:::::pairs 分かったこと | 打ち手
:::subject
返却の半分は閉館後の 20 時から 23 時に集まる
:::
:::response
- 返却箱を2つに増やす
- 箱が満ちたら翌朝の当番に知らせる
:::
::::subject
:::quote 利用者 B、聞き取りにて
返したのに延滞の知らせが来て驚いた
:::
::::
:::response
箱の中身は開館と同時に読み取る
:::
:::::
```

- 見出しの文は2つの側の見出しで、`|` で分ける(必須。文の中の `|` は `\|`)。前が
  `subject`(その対が何についてか:分かったこと・課題・問い)、後が `response`(それに
  応えるもの:打ち手・対策・答え)。どちらを左に置くかはテンプレートが決める。
- 中は `:::subject` と `:::response` を交互に書き、1組が1つの対になる(2組以上)。順が
  崩れたもの・`response` の無い `subject`・ほかのものは `misplaced-content`。
  `:::subject`・`:::response` を `pairs` の外に書くのも誤り。
- 側の中身は段落・箇条・`:::quote` のどれか1つか、**見出しと複数のブロック**(#87)。
  `:::subject 見出しの文` のように囲みの名前の後ろに書いた文はその側の見出し(短い文。文中の
  記法を読む。例:要因の名前)で、中には段落・箇条・`:::quote`・画像(1枚)・表を1〜4個
  書ける。見出しの無い側に2つ以上のブロック(または画像・表)を書いても同じ形になる。
  5個目のもの・`:::note`・コードブロックなどは `misplaced-content`。続きの表(`{continues}`)は
  置けない。引用を入れる側はコロンを1つ増やし(`::::subject`)、`pairs` はさらに1つ増やす
  (`:::::pairs`)。見出しの文が無く中がただ1つの段落・箇条・引用の側は、今までどおり
  1つのブロックの IR になる。

```
:::::pairs 特筆すべき点 | 聞き取りの声と実施事例
:::subject 家賃と広さが合わない
- 空き店舗の多くは 80 平米を超え、小さな店には広すぎる
- 家賃の相場は周りの通りより2割高い
:::
::::response
- 区切って貸せば借りたいという声が多い
:::quote 雑貨店の店主 A、聞き取りにて
半分の広さなら、来月にでも借りたい
:::
::::
…
:::::
```

  例は `examples/md/pairs-side-body.bx.md`(IR は `examples/ir/pairs-side-body.json`)。
  dark・light は側の見出し(太字の本文)と中のブロックを縦に積む。report は対ごとに
  A・B・C の四角い印を subject の頭に、2つの側の間に丸い山形の印を置き、対の間に罫線を
  引き、側の見出しを薄い面の帯の上に書く。
- **対の名前(label。#118)**:`:::subject {label=短い名前}` で、その対の短い名前(要因の番号・
  行の名前)を書ける。IR は対の `label`(`pairs.pairs[].label`)。見える字を含む12字までの文で、
  空白を含むときは `"` で囲む(`{label="夕方 18 時以降"}`)。空・13字以上は `invalid-value`
  (場所 `…/pairs/K/label`)。1つの `pairs` の中では、全ての `:::subject` に書くか、どれにも
  書かない(混ざれば `pairs-label`。場所は名前の有無が1つ目の対と違う対で、名前を書いた方なら
  `…/pairs/K/label`、書かなかった方なら `…/pairs/K`)。`:::response` には書けない
  (`unknown-attribute`)。描き方はテンプレートが決める:report は全ての名前が2字までなら
  A・B・C の代わりに四角い印の中に、3字以上の名前があれば印を置かず行の左に細い見出しの列
  (幅 80pt・基調色の太字。長い名前は列の中で折り返す)。dark・light は subject の頭に
  基調色の太字で。組み方を持たないテンプレートは subject のまとまりの頭の強調の段落にする。
  名前の無い pairs は今までどおり(report は A・B・C)。例は `examples/md/pairs-label.bx.md`
  (IR は `examples/ir/pairs-label.json`)。

```
:::::pairs 分かったこと | 打ち手
:::subject {label=1}
空き店舗の多くは 80 平米を超え、小さな店には広すぎる
:::
:::response
区切って貸せるよう、仕切りの工事に補助を出す
:::
:::subject {label=5}
…
:::::
```

- 属性は `pairs` の `variant` と `:::subject` の `label` だけ。幅や並べ方の属性は無い(`unknown-attribute`)。
- はみ出しは対ごとに測る(対の高さは2つの側の高い方)。`layout-overflow` は、はみ出した
  対を `/slides/S/body/N/pairs/K` で指す。容量(`check -format json`)の `pairs` に
  対ごと・側ごとの高さが出る。見出しと複数のブロックの側の高さは、見出しと body の
  ブロックを積んだ高さ。

### 3.11 印つきの塊の並び(topics)

いくつかの観点を、それぞれ題と説明で上から順に並べる。塊ごとに短い印(A・B・C)を
付けられる。標準でない型で、組み方を持たないテンプレートでは箇条(題を親、中身を子)で
組まれる(警告 `component-fallback`。`docs/ir.md` の設計判断10.2)。例は
`examples/md/topics.bx.md`。

```
:::::topics
:::topic 通いやすさ {label=A}
- 徒歩 15 分より遠い人には、近くの空き区画を先に案内する
:::
:::topic 続けやすさ {label=B}
初めての人には、相談役の区画の隣を割り振る
:::
::::topic 公平さ {label=C}
抽選の結果と理由を、掲示板と便りの両方で知らせる

:::quote 利用者 D、聞き取りにて
外れた理由が分かれば来年も申し込める
:::
::::
:::::
```

- 中は `:::topic 題の文` を2〜6個(数が外れると `misplaced-content`)。題の文は必須
  (無ければ `missing-key`)。`:::topic` を `topics` の外に書くのも誤り。
- `{label=A}` は塊の短い印(空白を含まない2字まで。外れると `invalid-value`)。全ての
  `:::topic` に付けるか、全てに付けない(混ぜると `invalid-value`)。
- 塊の中身は段落・箇条・`:::quote` の1〜3個。4個目・表・画像・`:::note`・コードブロックは
  `misplaced-content`。引用を入れる塊はコロンを1つ増やし(`::::topic`)、`topics` はさらに
  1つ増やす(`:::::topics`)。
- `::::topics` の属性は `variant` だけ、`:::topic` の属性は `label` だけ(ほかは
  `unknown-attribute`)。
- dark・light は題を太字にして印を題の頭に書く。report は左に丸い印、右に基調色の題と
  中身、塊の間に罫線。
- はみ出しは塊ごとに測る。`layout-overflow` は、はみ出した塊を `/slides/S/body/N/topics/K`
  で指す。容量(`check -format json`)の `topics` に塊ごとの高さが出る。
- 並列のまとまりの中にも置ける(#129。左に概要、右に A・B・C の塊)。塊は本文と同じく縦に
  積む。コロンは外側ほど多くする(引用を持つ塊があれば `::::topic`・`:::::topics`・
  `::::::column`・`:::::::columns`)。組み方を持たないテンプレートでは、まとまりの中でも
  箇条で組む(`component-fallback` の場所は `…/columns/C/body/K`)。まとまりの中では
  はみ出しを塊ごとには測らず、`columns` のブロックとして測る。


### 3.12 人物の紹介(people)

写真・名前・役職・経歴を並べる(標準でない型。IR は `docs/ir.md` の10.3)。例は
`examples/md/people.bx.md`(人物と写真は架空)。

```markdown
::::people
:::person 森川 あおい {role=主任研究員 image=images/person-a.png alt="森川 あおいの似顔絵"}
- 地域の交通の調査を 12 年
- 聞き取りの設計と全体のとりまとめ
:::
:::person 高木 美里 {role="商店会 会長"}
商店街の聞き取りの段取りに協力いただく
:::
::::
```

- `:::person` の後ろが名前(必須。無ければ `missing-key`)。属性は `role`・`image`・`alt` だけ。
  空白を含む値は `"…"`(か `'…'`)で囲む(どの囲みの属性でも同じ)。
- `image` を書いたら `alt` も要る(`missing-key`)。`alt` だけは誤り(`misplaced-content`)。
- 中は経歴の段落か箇条を1つ。2つ以上・囲み・表は `misplaced-content`。`::::people` の中には
  `:::person` だけ、人は1〜4人。
- 並列のまとまりの中にも置ける(1〜2人、縦に積む)。`columns`・`column` は入れ子の段に数えないが、
  コロンは外側ほど多くする:

```markdown
::::::columns
:::::column 問い合わせの窓口
::::people
:::person 森川 あおい {role=主任研究員}
調査の全体について
:::
::::
:::::
:::::column 受け付ける時間
- 平日の 9 時から 17 時
:::::
::::::
```

## 5. 誤りの返し方(`boxloom check`)

`boxloom check -format json deck.bx.md` は、誤りを1件ずつ次の形で返す。Markdown の
パーサー(`parse`)・`boxloom check`・`tools/validate_ir.py` は、どれもこの形で出す。

```json
{
  "file": "deck.bx.md",
  "line": 14, "column": 1,
  "path": "/slides/0/body/1",
  "code": "unknown-attribute",
  "message": "属性 color はありません。見た目はテンプレートが決めます",
  "expected": ["variant", "id"],
  "hint": "強調したいなら **…** か、テンプレートの variant を使ってください"
}
```

- `line`・`column` は Markdown の中の場所。**IR(JSON)を直接検査したときは出さない**。
  Markdown の記法が通ったあとの意味の誤り(日付が範囲の外など)は、IR の場所から
  引いた行だけを付ける(`column` は無い)。
- `path` は IR の中の場所(JSON Pointer)。いつも出す(`""` は文書全体)。
- `expected`(選べるもの)と `hint`(直し方)は、あるときだけ出す。
- `code` は決まった一覧(`unknown-block` `unknown-attribute` `raw-html` `unsupported-syntax`
  `unclosed-block` `schema` `layout-overflow` …)。AI はこれで分岐できる。
- テンプレートの規則の検査(はみ出し・fill-ratio など)も同じ形で返す。
  `layout-overflow` のときは、どの意味ブロックがどれだけはみ出したかを付ける。
- 警告(fill-ratio など)は `warnings` に同じ形で入る。
- 終了コードは、誤りがあれば 1、警告だけなら 0(`-strict` なら警告も 1)。
- `code` の全部の一覧は、記法の誤りが8章、意味の誤りと警告が `docs/ir.md` の
  「意味の検査」の節。

## 6. AI に書かせるときの決まり

- `boxloom schema` で、いまのテンプレートとサブシステムが名乗る囲み・属性・
  サブシステムの Schema を、まとめて JSON で出す。AI にはこれを渡す。
  `-template 名前` でそのテンプレートの分だけに絞る。出力の形は
  `docs/schema-command.md`(IR を直接書くための Schema も `irSchema` に同梱する)。
- 推奨の流れ: 書く → `boxloom check` → 誤りを渡して直させる、を誤りが無くなるまで回す。
- 構造化出力で確実に書かせたいときは、Markdown ではなく IR(JSON)を直接書かせてよい。
  `boxloom fmt --to md` で IR から Boxloom Markdown に戻せるようにする(往復できること)。

## 7. まだ決めていないこと

- 拡張子(`.bx.md` 案。パーサーは `.md` で終わるものをすべて読む)。
- スライドの `id` を IR に足すか。`takeaway`(3.4)と `columns`(3.9)は入った。
- (決めた)**小見出し(`##`)は持たない。** 小見出しは Markdown の書き方の都合で、
  意味ではない。IR は意味から設計し、記法の都合を持ち込まない。`##` 以下の見出しは
  誤りのまま。まとまりに名前が要るなら、それは意味の型(例:`columns` の各まとまりの
  題)として IR に持ち、Markdown では囲みの見出しの文(`:::名前 見出しの文`)で書く。
- (決めた)**表と画像は第1層のブロックにする**(サブシステムにしない)。表は `table`、
  画像は `image`(1枚)と `gallery`(2〜6枚)。理由と決まりは `docs/patterns.md` の
  2.1・2.2、書き方は 3.7・3.8。
- 1つの文書を複数ファイルに分ける方法(取り込み)。
- 囲みの属性の値の型(文字列だけか、数や真偽値も許すか)。いまは文字列だけ。空白を含む値は
  `"…"` か `'…'` で囲む(#120。`{role="商店会 会長"}`)。

## 8. パーサー(Go 版)

```sh
cd boxloom
go run ./cmd/boxloom parse ../examples/md/demo-deck.bx.md            # IR(JSON)を標準出力に書く
go run ./cmd/boxloom parse -format json deck.bx.md                   # 誤りを {"ok": false, "errors": [...]} で出す
go run ./cmd/boxloom build ../examples/md/demo-deck.bx.md            # .md もそのまま PPTX にする
```

- 拡張子が `.md`(`.bx.md` を含む)なら Markdown として、それ以外は IR の JSON として読む。
  出力の名前は `deck.bx.md` → `out/deck.pptx`。
- 誤りは最初の1件で止めず、読めるところまで全部集めて、行の順に返す。形は5章の形
  (`file`・`line`・`column`・`path`・`code`・`message`・`expected`・`hint`)。
  `-format text`(既定)は `file:line:column path: code: message` の1行ずつ。
- いまの `code` の一覧:`unknown-block`・`unknown-attribute`・`raw-html`・
  `unsupported-syntax`・`planned-syntax`(仕様で「予定」のもの)・`unclosed-block`
  (囲み・コードブロック・強調・コロンの数の不一致)・`misplaced-content`(その場所に
  書けないもの。例 `:::option` を `:::compare` の外に書いた)・`unknown-key`・
  `missing-key`・`invalid-value`(YAML と文書の頭の値・`role` の値)・`yaml`(YAML の部分集合の外)・
  `table-shape`(表の行のセルの数が見出しと違う)・`table-points`(`{points=列名}` の列名が
  見出しに無い・セルの箇条の項目が空)・`table-groups`(`{groups=…}` の表の
  最初の行の群の名前が空・左の群の列で群が始まる行の右の群の列のセルが空)・`table-continues`(`{continues}` の表に見出しの行を書いた・
  前の表と列の数や groups・points が違う・前のスライドに続ける表が無い)・`pairs-label`(`::::pairs` の
  中で `{label=…}` のある `:::subject` と無いものが混ざった)・`image-path`(画像の path が URL・
  絶対パス・文書のフォルダの外)・`image-alt`(画像の代わりの文が無い)・
  `schema`(できた IR が通らない。ふつうは起きない)。
- shapes と図(process・orgchart・matrix・funnel・phases・cycle・pillars)と chart のコードブロックは、YAML の形の検査
  だけをする(サブシステム自身には読ませない。意味の誤りは `boxloom check` が行つきで返す)。
- Gantt のコードブロックは、YAML の検査が通ったあと Gantt サブシステム自身にも
  読ませる。Schema では書けない誤り(`target` の行き先が無い・id の重複・範囲の
  前後)もここで見つかる(このときの `line` はコードブロックの開きの行)。
- `boxloom check` は `.md` も受け取る(記法の誤り → 無ければ IR の意味の検査と
  組み立ての警告。`docs/ir.md` の「意味の検査」)。`layout-overflow`(はみ出し)の
  検査はまだ無い。
