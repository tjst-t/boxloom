# AI に同じ題材を python-pptx の直書きと Boxloom で作らせて比べる(#16)

出発点の仮説(2)は「破綻(重なり・はみ出し)の心配が無ければ、AI は薄いレイアウトに逃げず、
密度の高い図に挑む」。これを数で確かめた。1回目の結果(2026-11-16、コミット 0fc8080 の上)。

**結論:この条件では仮説(2)は支持されなかった。** Boxloom で作った資料は、1枚あたりの
文字は 9% 多い。一方で、要素の数と埋まり具合は python-pptx の直書きより低く、作り直しは
2.5倍だった。直書きの側も、目で見て崩れている所は1か所(矢印が右の余白に少し出る)だけだった。
画像を見ながら直せる AI は、破綻を恐れて薄くしてはいなかった。
Boxloom が確かに勝ったのは「機械で測った重なり・はみ出しが0」のほうで、これは仮説(1)の側の話。
詳しくは5節。

## 2. 手順

- **作り手**:サブエージェント4つ(Claude Opus 5.5。やり方ごとに2つで、それぞれ5本)。
  同じ題材を2つのやり方で作る。片方のやり方の作り手は、もう片方の成果物を読めない。
- **共通の指示**:表紙1枚+本文3枚の 16:9。会議で映して説明し、配って読み返してもらう資料。
  材料は全部使わなくてよい。画像は使わない。出来上がりは画像で見て、良いと思えるまで直してよい。
  **密度・この評価の仮説には触れていない。**
- **python-pptx**:`pptx/tNN.py` を書く(python-pptx 1.0.2。字体は Noto Sans CJK JP が入っている)。
- **Boxloom**:`skills/boxloom/SKILL.md` に従い `boxloom/tNN.bx.md` を書く。テンプレートは作り手が選んだ
  (report が8本、light が2本)。
- **作る・見る**:どちらも `examples/density-eval/run.sh` だけを使う。PPTX を作り、LibreOffice で1枚ずつ
  PNG にする。Boxloom は加えて `check -format json` を出し、`build` する(-fit なし)。
  run.sh は呼ぶたびに `runs.log` に1行を足す。**作り直し**は「呼んだ回数 − 1」。
- **測る**:`tools/density_metrics.py`。作り方によらず、できた PPTX だけを同じ物差しで測る。
  本文の3枚が対象(表紙は除く)。
  - 要素:見える葉の図形の数。グループは中を数え、表・グラフは1つ。
  - 文字:空白を除いた字の数。図形・表のセル・グラフの項目と系列の名前を含む。
  - 重なり:線・コネクタと、スライドの大半を覆う地は除く。部分の重なりと、文字を持つ要素どうしの
    交わりを数える。噛み合わせて並べる山形の矢印どうしは数えない。地も枠線も無い文字だけの枠は、
    字のある幅を矩形にする。
  - はみ出し:2つを数える。1つは、文字が枠に入らないこと(Noto Sans CJK JP の寸法で折り返しを見積もる。
    行の送りは spcPts、無ければ 1.2×字の大きさ×倍率)。もう1つは、スライドの外に出る要素
    (表は行が伸びた後の高さで見る)。
  - 埋まり:地を除いた要素の矩形の和の面積 ÷ スライドの面積。
  - 試しに、Boxloom の既存の評価資料3本(`examples/eval/`)を測った。重なり・はみ出しは0件で、
    誤検出は出なかった。

```sh
cd examples/density-eval
sh run.sh pptx t01          # pptx/t01.py → out/pptx/t01.pptx と画像
sh run.sh boxloom t01       # boxloom/t01.bx.md → check・build → out/boxloom/t01.pptx と画像
python3 summarize.py        # 全部を測って results.json と表(下の3節)
```

## 4. 作り直しの中身

作り手の報告と `runs.log` から分けた。

| 理由 | pptx(9回) | Boxloom(23回) |
|---|---|---|
| 崩れを目で見つけて直した(折り返し・重なり・余白) | 6(見出しの折り返し4、線とラベルの重なり1、帯の空き1) | 5(表紙の題・副題の折り返し2、列の見出しの折り返し・グラフが狭い2、リードの残り1字1) |
| 道具の警告で直した | — | 10(fill-ratio 9、layout-overflow 1) |
| 書き方の誤り(build できない) | 0 | 2(YAML の値のカンマ、箇条の段の混ぜ方) |
| 中身・言い回し(材料に無いことを消すなど) | 3(影・書式の掃除を含む) | 6 |

- Boxloom の作り直しの多くは **fill-ratio**(薄いので足す)が理由だった。警告は「もっと載せよ」の方向に
  働いた。それでも埋まりは直書きに届いていない(3節の空き)。
- Boxloom の layout-overflow は1回だけだった(t09。matrix が 2.6pt はみ出し、行を1つ削った)。はみ出しに
  当たって薄くした例は、ほかには無い。
- 直書きの側も、崩れは画像を見て直していた。t04・t07 は1回目で良しとした。

## 5. 仮説は支持されたか

**支持されなかった(この条件では)。**

- 仮説(2)が言う行動は「破綻を恐れて薄いレイアウトに逃げる」。しかし直書きの AI は逃げていなかった。
  要素の数は 22.2/枚で、埋まりは 55%。図形でグラフ・数直線・線表を自分で描いていた。崩れの見落としは
  10本で1か所だった。
- Boxloom の側の密度は、文字こそ多い(+9%)ものの、要素・埋まりは低い。差は題材によって入れ替わる
  (10本のうち要素は4本、文字は6本で Boxloom が上)。はっきりした差とは言えない。
- 違いがはっきり出たのは2つ。
  - 機械で測った重なり・はみ出しの数(pptx 9、Boxloom 1。ただしどちらも画像では崩れでなかった)
  - 作り直しの回数(Boxloom が多い。主に fill-ratio)
- 前者は仮説(1)の側の話。直書きの「機械で見ると枠ぎりぎり」の所は、字体が置き換わる環境
  (`docs/fonts.md`)では崩れになり得る。Boxloom は測った上で組むので、その心配が構造的に小さい。
  ここは Boxloom の価値として残る。

### 5.1 この評価の限り

- 作り手は1つのモデル(Opus 5.5)だけで、どちらの側も **画像を見て直せた**。仮説(2)が想定したのは
  「見た目を確かめられない(または確かめるのが重い)AI が、安全のために薄くする」状況だったと思われる。
  画像を見る道を断てば、結果は変わり得る(次の評価の候補:画像なし、または小さいモデル)。
- 埋まりは要素の矩形の和で、Boxloom の淡い地・余白の取り方と、直書きの塗った帯とを同じに数える。
  見た目の密度とは完全には一致しない。
- はみ出しの見積もりは LibreOffice に合わせた行の送り(1.2倍)で、PowerPoint では違い得る。直書きの
  はみ出し5件は画像では見えなかった。
- 10本・本文30枚ずつ。差の検定はしていない。
